## Зачем оно нужно

RustFS — объектное хранилище с S3-совместимым API. Здесь приложения сохраняют файлы отдельно от своей базы данных: например, диагностические материалы к SPI-инцидентам. GitHub содержит описание инцидента и ссылки, а сами материалы лежат в хранилище.

**Bucket** — именованный контейнер объектов. **Key** — полное имя объекта внутри bucket. Например, `spi/v1/<jobHash>/<snapshotHash>/manifest.json`. Слеши выглядят как папки, но это префиксы имён, а не обычная файловая система. Не нужно монтировать bucket как диск для просмотра файлов.

## Три разных входа

| Вход | Для чего | Как авторизоваться |
|---|---|---|
| [Консоль RustFS](https://rustfs.socrat.alchemmist.xyz/rustfs/console/browser/) | Просматривать buckets и объекты; управлять при выданных правах | Личный Authentik / SSO |
| Защищённые ссылки `https://spi-evidence.socrat.alchemmist.xyz/spi/v1/…` | Читать конкретные SPI-материалы по ссылкам из GitHub | Личный разрешённый сеанс Authentik |
| Внутренний S3 API `http://rustfs.rustfs.svc.cluster.local:9000` | Программный доступ приложений и CLI | Отдельные scoped S3 credentials |

Адрес консоли — **не автоматически адрес внешнего S3 API**. Внутреннее DNS-имя доступно из разрешённой среды кластера; оно не обязано работать с вашего Mac. Перенос защищённых загрузок на единый RustFS-домен подготовлен, но **приостановлен и не развёрнут**: пользуйтесь существующими ссылками `spi-evidence`.

Новый bucket не требует нового домена: доступные buckets показываются в одной консоли RustFS.

## Посмотреть и скачать через браузер

1. Откройте консоль и войдите своей учётной записью Authentik.
2. Выберите bucket `spi-evidence`.
3. Откройте префикс `spi/v1/`, затем нужные `jobHash` и `snapshotHash` из ссылки инцидента.
4. Сначала скачайте `manifest.json`: это перечень материалов снимка, их размеров, хешей и ограничений сбора.
5. Выберите нужный объект по имени из manifest и используйте действие скачивания. Через ссылку из GitHub тот же материал доступен в защищённом reader.

Ссылки не становятся публичными от помещения в GitHub: при необходимости пройдите Authentik и повторно откройте ссылку. Reader отдаёт вложения с безопасным именем и `nosniff`; это не механизм встраивания приватных картинок в GitHub. PNG/inline-просмотр пока не реализован.

## Как это используется сейчас

По проверкам **7 ноября 2026 года**, SPI сохраняет неизменяемые снимки диагностик в bucket `spi-evidence`. В первичных публикациях для инцидентов [№75](https://github.com/alchemmist/homelab/issues/75) и [№88](https://github.com/alchemmist/homelab/issues/88) есть ссылки на manifest и отдельные артефакты. Под одним префиксом находятся `manifest.json` и материалы с идентификаторами вида `E003`; точное имя берите из manifest, а не придумывайте расширение.

Схема размещения:

```text
spi-evidence                    ← bucket
└── spi/v1/<jobHash>/<snapshotHash>/
    ├── manifest.json
    └── …                       ← объекты E###, перечисленные в manifest
```

Manifest фиксирует размеры и SHA256, а также недоступные источники, усечение и другие ограничения. Наличие manifest **не означает**, что собрана вся телеметрия или что отсутствие ошибок доказывает здоровье сервиса. Число объектов меняется по мере обычной работы; это не фиксированный каталог примеров.

Приложение не должно перезаписывать конфликтующие SPI-объекты. Не загружайте свои файлы в управляемый SPI-префикс и не удаляйте материалы ради освобождения места без согласованной политики хранения.

## CLI: только чтение

Для CLI нужен отдельный профиль с разрешёнными минимальными S3-правами. Браузерный SSO-сеанс — не постоянная пара AWS access key / secret key. Попросите администратора выдать или согласовать scoped учётные данные/служебную учётную запись и настройте профиль безопасно. Не используйте общий root и не копируйте ключ приложения. Создание производных ключей из временной OIDC-сессии зависит от ограничений версии и политики; наличие кнопки в консоли не гарантирует разрешение.

Следующие команды иллюстративные и выполняются **только из разрешённой среды с доступом к внутреннему endpoint**. Замените `<your-s3-profile>` на заранее настроенный профиль; секретов в командах нет.

```bash
aws --profile <your-s3-profile> \
  --endpoint-url http://rustfs.rustfs.svc.cluster.local:9000 \
  s3 ls s3://spi-evidence/spi/v1/

aws --profile <your-s3-profile> \
  --endpoint-url http://rustfs.rustfs.svc.cluster.local:9000 \
  s3 cp s3://spi-evidence/spi/v1/<jobHash>/<snapshotHash>/manifest.json ./manifest.json
```

Не передавайте ключи через URL, чат или скриншоты. Здесь намеренно нет команд записи и удаления. Для собственных загрузок сначала согласуйте отдельный bucket или префикс вне неизменяемых SPI-данных.

## Права и частые вопросы

**Почему раньше было No Buckets?** Роль reader не равна администратору хранилища. Для личной учётной записи владельца `alchemmist` отдельно разрешена полная роль `consoleAdmin`. Старый сеанс может сохранять предыдущую роль: выйдите именно из RustFS и войдите заново через Authentik. Это не общий root-пароль и не повышение прав всех пользователей.

**Почему вижу 403?** Права консоли, S3 API и защищённого reader различаются. Сообщите администратору адрес сервиса, время, действие и название профиля/учётной записи без ключей и cookies. Не пытайтесь обходить запрет другим общим ключом.

**Можно удалять из консоли?** Полный администратор может выполнять опасные операции. Удаление bucket или объекта ломает опубликованные ссылки; права не заменяют согласование удаления и резервную копию.

**Ссылки вечные?** В них нет срока действия presigned URL, но это не гарантия вечного хранения. Доступ зависит от авторизации, сохранности объекта и административной политики хранения.

## Где хранится и что не гарантируется

На 7 ноября 2026: standalone RustFS на `socrat-0`, retained PVC `20Gi`, память request `2Gi`, limit `4Gi`; S3 Service — порт `9000`. Эти параметры проверены чтением конфигурации работающего сервиса. Запрошенные `20Gi` — не обещание принудительной файловой квоты. Retain помогает не удалить том вместе с ресурсом Kubernetes, но **не является резервной копией**.

Это не HA-кластер и не доказательство регулярных независимых резервных копий. Потеря единственного узла/диска требует отдельного восстановления. Перед опасными административными действиями проверяйте актуальную процедуру backup/restore.
