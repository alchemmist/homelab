Решения по архитектуре автоматизаций и умного дома (Яндекс). Принято 2026-10-12. Страница фиксирует границы между подсистемами, чтобы агенты и люди не плодили дублирующие сценарии.

## Контекст: доступ к умному дому Яндекса

Умный дом доступен через два независимых канала, оба проверены вживую:

| Канал | Транспорт | Для чего |
| --- | --- | --- |
| Лампы, розетки, светильники, сценарии («Чай», «Вечер» и др.) | Облачный IoT API `https://api.iot.yandex.net` (scope `iot:view`, `iot:control`) | Включение, яркость, цвет (HSV и температура), запуск сценариев |
| Яндекс Станция Миди: озвучка (TTS), громкость, медиа | Локальный WebSocket `wss://192.168.0.17:1961` (протокол «глагол», payload `update_form` → `repeat_phrase`) | Голосовые уведомления: алерты, напоминания из календаря |

Особенности, которые надо помнить:

- IoT API не принимает `quasar.action`: озвучить текст через облачный API нельзя, для Станции работает только локальный протокол.
- Токен для ламп и сценариев живёт в `~/.config/yandex-iot/token`. Cookies Яндекс-сессии (для цепочки x-token → music token → device token Станции) хранить как пароль. В кластере оба секрета уходят в Kubernetes Secrets, не в код и не в образы.
- У облака Яндекса нет webhook'ов: состояния устройств доступны только опросом.
- Станция не отвечает на ICMP, но порт 1961 доступен из домашней LAN. Клиентские машины с VPN-туннелями иногда теряют маршрут до LAN, поэтому сервисы, работающие со Станцией, запускать на узлах кластера, а не на ноутбуках.

Home Assistant в этой схеме сознательно не используется: все текущие сценарии решаются прямыми API. HA остаётся опцией на случай появления устройств с локальными протоколами (Zigbee, Matter).

## Двухслойная архитектура автоматизаций

Каждая автоматизация строится по одной схеме:

1. **Capability-сервисы** — тонкие stateless HTTP-обёртки над физическими каналами. Код в гите, деплой Helm-чартами в `charts/`, секреты в Secrets. Внутри нет бизнес-логики. Планируются:
    - `voice`: `POST /say {text}` — озвучка через Станцию.
    - `yandex-home`: управление лампами, розетками и сценариями через IoT API (цвет, яркость, вкл/выкл, запуск сценария).
2. **n8n** — единый оркестратор событийной логики. Вся логика «что, когда, при каких условиях и кому» живёт в нём: календарь → напоминание голосом, webhook алертов → TTS + красный свет, будущие правила про дом и расписание. Один сценарий = один workflow, виден в UI, включается тумблером. n8n знает о capability-сервисах только по HTTP и не содержит яндексовых токенов.

n8n разворачивается self-hosted в кластере (лицензия Sustainable Use разрешает внутреннее использование). Workflow версионировать экспортом JSON в гит рядом с чартом.

## Граница: CronJob Kubernetes vs n8n

Оба механизма «делают что-то по расписанию», но относятся к разным слоям. Правило:

- **CronJob в K8s** — инфраструктура: работа с данными и кластером без пользовательской логики. Перекладка метрик, ротация бэкапов, сбор мусора, обновление сертификатов. Существующая джоба метрик остаётся здесь и не мигрируется.
- **n8n** — события из внешнего мира и логика про «мой день и мой дом»: уведомления, календарь, алерты, умный дом, Telegram.

Дополнительное правило: **у каждого сценария ровно один владелец**. Задача не выполняется одновременно через CronJob и n8n, иначе двойные срабатывания и ад при отладке. При сомнении, куда класть новую задачу: нет пользовательского условия и внешнего события → CronJob; есть «если X, то уведоми/сделай» → n8n.

## Правила для агентов

- Не встраивать вызовы яндексовых API с токенами прямо в workflow n8n — всегда ходить через capability-сервисы.
- Новые умные сценарии добавлять в n8n, не плодить отдельные поды с cron-логикой.
- Напоминания и алерты озвучиваются только через `voice`-сервис; WebSocket Станции нигде больше не открывать.
- Изменение этой страницы сопровождать обновлением соответствующих чартов в `charts/`, чтобы wiki и код не расходились.
