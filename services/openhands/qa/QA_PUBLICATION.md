# QA owner authorization and publication
Owner has authorized autonomous QA issues and QA PRs in alchemmist/monori. Do NOT ask again per issue or PR. This QA interface supersedes previous notes that only drafts are supported. No personal token, merge, production, arbitrary uploads, or write to main. English on GitHub; Russian to owner.

POST JSON to http://monori-publisher:8081/v1 from the workspace (stdlib urllib is sufficient). Actions:
- `qa_capabilities`: safe discovery.
- `qa_issue`: keys exactly `action,key,title,kind,head,steps,expected,actual,pngs,reviewed_synthetic`. `key` is a stable lowercase slug, 5–65 alphanumerics/hyphens, reuse on retries. kind `bug` or `improvement`. `head`: full tested commit. Other text fields plain English prose without mentions, URLs or HTML. `pngs`: ordered array of 1–4 base64-encoded INDIVIDUALLY reviewed safe synthetic PNG files, <= ~800KiB each, <=3MP each. Use a coherent evidence sequence (baseline, click/filter, after). Never send a folder, token.json, logs, HAR, screenshots with secrets or real personal data, never upload first and inspect later. Inspect actual pixels, not just DOM/size; if unsure recapture a controlled safe view. Set `reviewed_synthetic:true` only after review. No MP4 support in this channel: use a sequence of screenshots. Returns real issue URL and inline PNG references. Verify accessible links after publication. If behavior is reproducible but no requirement makes it a defect, say so and propose an improvement, or reject the finding. Search duplicates first; stable key handles exact retries. Do not invent quotas/findings.
- Batch discovery before fixing. `qa_create`: keys `action,issue,head,title,files`; only for an open QA issue created by this publisher, head = current main SHA, files = map repo-relative allowed source/test paths to complete UTF-8 file contents. One open publisher PR per issue. No workflow/dependency files, generic requests, or merges. Use a separate worktree per PR.
- `update`: action,pr,head,title,files (head must be current). `threads`, `report`: action,pr,head. `reply_then_resolve`: action,pr,head,thread,decision (`fixed` or `declined`),reason. Use after evaluating evidence. No duplicate replies, review all checks at current SHA. Human alone merges.

Persist issue URL, media links, head SHA, PR and next step in QA_PROGRESS.md. On a real technical failure note the exact stage and continue independent permitted tasks. Do not re-request approval for publication. Manual pause stays respected. No mutations/#509.

### Browser recordings
For new findings include a short MP4, not just milestone screenshots. On a fresh synthetic loopback context use `require('/home/openhands/.openhands/tools/record.cjs').record(page, freshDirectory, async()=>{ /* actual clicks + reload */ })`. Use an even-sized viewport <=1280x800, visible click/reload and actual vs expected result, <=30s. Review the entire sequence (not just first/last frames), only safe synthetic pixels. Add `frames` to the existing `qa_issue` JSON payload: ordered base64 JPEG strings from this **one recording**, 6fps, 12–180 frames, <=20MB total JSON. Keep 1–4 reviewed summary PNGs. The publisher encodes H.264 MP4 from pixels and appends a viewer and download link. Never pass arbitrary file paths, whole evidence directories, logs, tokens, personal data or real sessions. Existing deduped issues are not rewritten by qa_issue.

### Sequential campaign — authoritative on admission
Do not start a new fix on every discovery. Finish discovery first: target about ten independent validated findings, never a quota. If fewer, record scenarios actually exhausted and the reason for transition. No invented bugs. Preserve existing #512 work and do not duplicate it. Maintain QA_PROGRESS.md on the PVC: phase, tested scenarios (including negative results), finding/issue and verified MP4, assigned task_id/worktree, PR/current head, before/after UI proof, required CI, bot reviews/threads, blocker and exactly one next action. Only the coordinator writes the campaign ledger; children return evidence. Reconcile it with GitHub on resume, not with a model summary alone.

Then take ONE outstanding issue at a time. Reproduce first, fix in an isolated worktree, regression + browser retest with the original scenario and before/after evidence, publish PR. On the latest head repair failing CI, assess each bot comment, fix or explain and reply before resolving. Recheck after every SHA change. Ready requires all required checks passed and independent bot reviews for that head. No merge by agents. Record ready and move to next issue without waiting for human merge. Closed unmerged is not ready. A merged PR ends only that item. A worker finishing, waiting for CI, or model outage is never campaign completion. On outage preserve cursor, do not flood requests. Respect manual pause. Use a child for bounded context, not for throughput.
