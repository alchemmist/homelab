# Публичный HTTP в Socrat: один маршрут приложения, три входа

**Предложение к утверждению.** Для Москвы используем существующий IP `91.189.82.238`. Второй IP не покупаем. Обычный HTTPS завершается на московском Traefik, а не в Нидерландах. Существующий VPN сохраняет свой транзит в NL. Ни размещение primary PostgreSQL, ни публичная доступность конкретного backend этим решением не меняются.

```text
HOME → домашний Traefik ─────────────────────┐
NL   → traefik-edge на socrat-2 ─────────────┼→ Service приложения → готовый endpoint
MSK  → HAProxy → Traefik на socrat-4 ────────┘
          └→ неизвестное имя / VPN / нет SNI → прежний TCP-транзит → NL
MSK UDP → прежний UDP-транзит (без HAProxy)
```

### На чём основано решение

- На `socrat-4` сейчас один публичный IPv4, TCP 80/443 и UDP 443 заняты. [Конфигурация транзита](../../deploy/vpn-hardening/moscow-transit.json) задаёт для TCP 80/443 фиксированный адрес NL без анализа SNI. Поэтому установка второго процесса на эти же порты не решает задачу.
- С самого `socrat-4` запрос к **ClusterIP** Argo с настоящим SNI и проверкой сертификата вернул `200` за 171 мс (`/api/version`, backend на `socrat-0`). Проверка готовности Authentik через его Service вернула `200` за 105 мс. RTT с Москвы до WG-адреса HOME — 14 мс, до `socrat-5` — 6–16 мс. Для доступа Москвы к сервису не требуется публичный HTTPS-вход NL. Это не испытание отключением NL.
- В изолированном контейнере HAProxy 3.2 с двумя моделями backend один TLS-порт отправил объявленное веб-имя на `WEB`, VPN-имя и реальный ClientHello без SNI — на `LEGACY`. Сертификат для именованных запросов проверял клиент. Это проверка диспетчеризации, не заявление о совместимости каждого рабочего VPN-клиента.
- В момент замера на VPS было около 208 МиБ доступной памяти; Kubernetes показывал около 327 МиБ allocatable **всего**, не свободных. Не резервируем последний запас под второй тяжёлый стек.

### PR 1. Единый список публикаций

Добавить `deploy/public-web/entrances.yaml`: имя хоста, namespace, допустимые входы, режим DNS и исключения. Перенести существующие публичные имена без расширения доступа; VPN и закрытые хосты не получают обычную веб-публикацию. Для schoolbot запись — `bot.sch1357.ru`, namespace `schoolbot`, DNS `external`. Маршрут, Service и TLS Secret по-прежнему задаёт **один** Ingress приложения. Декларация не дублирует пути и адреса Pod.

Из этого списка рендерить точные имена для московского HAProxy и списки namespace/RBAC для публичных контроллеров. HOME сохраняет текущие внутренние маршруты; запись Ingress status остаётся за одним контроллером. Для публичных namespace запрещать неучтённые Ingress-хосты и wildcard в проверке PR; смешанный приватный namespace не добавлять целиком. Использовать существующие Secrets cert-manager, без копирования ключей. Оставить только явно разрешённые CRD-транспорты (в частности, проверяемый TLS до Argo); `insecureSkipVerify` не вводить.

### PR 2. Локальный вход на Москве без захвата работающего VPN-порта

1. Выделить из `charts/traefik-edge` профиль **web-only** и отдельное Argo Application для `socrat-4`: локальные входы `127.0.0.1:18080` и `:18443`, доступ к Kubernetes API не через NL; без NL panel, подписок, Trojan и без второго владельца сертификатов. Использовать маршруты Service/EndpointSlice, а не статические Pod IP. Сначала развернуть без публичного трафика. Ограничить память и число соединений; если планировщик не вмещает резерв плюс новые процессы или нагрузочная приёмка вызывает вытеснение, увеличить RAM VPS **до** включения, а не отключать защиту ресурсов.
2. Установить HAProxy под systemd на альтернативные TCP-порты `10080/10443`. На HTTPS читать ClientHello без завершения TLS: точное SNI из списка → `127.0.0.1:18443`; VPN, неизвестное имя, отсутствие SNI или истечение ограниченного времени разбора → `127.0.0.1:443`, где остаётся прежний транзит. На HTTP объявленный Host, включая путь HTTP-01, → `127.0.0.1:18080`; остальное → прежний `127.0.0.1:80`. Не добавлять PROXY-заголовок в поток старого транзита. Для веб-ветки доверять информации об исходном адресе только от локального диспетчера, не от произвольного клиента.
3. В Ansible добавить одну атомарно включаемую цепочку **только для входящих через eth0 TCP-пакетов** к публичному адресу на 80/443: перенаправление на 10080/10443. Не затрагивать loopback, OUTPUT, UDP, внутренний WireGuard, DNS и дополнительные VPN-порты. Прямой внешний доступ к альтернативным портам закрыть; разрешить только перенаправленные соединения. Прежние порты и systemd fallback остаются на месте, сам транзит не перезапускается. При снятии цепочки новые соединения сразу идут по прежней схеме. Активные TCP-сессии не сбрасывать очисткой conntrack.

### PR 3. Ввод по одному имени, без массового переключения DNS

Сначала добавить в московскую карту одно тестовое имя. До изменения DNS оператор открывает его принудительно по московскому адресу: валидный TLS, HTTP-01, правильное тело, отказ на закрытом маршруте. Для контрольного backend исключить NL **только в тестовом пути**, подтвердить ответ логами московского ingress и конечного Pod. Одновременно действующий и новый VPN-клиенты должны работать; проверить применяемые TCP/UDP профили, отсутствие подмены IP в политиках доступа и возврат старого пути снятием цепочки. Невыполнение любого из этих условий блокирует публикацию. Это приёмка нового компонента, который сейчас ещё не развёрнут.

Затем включить `bot.sch1357.ru` после готовности приложения и сертификата; Данила меняет только A-запись `bot` у REG.RU на московский IP. Следующими партиями перенести обычные сервисы, сохраняя авторизацию и отдельные политики Monori и VPN. Для своих зон все авторитетные DNS публикуют одинаковый набор допущенных здоровых входов для конкретного имени, а не IP ответившего NS. Не публиковать NL для пользователей только потому, что нода отвечает по внутренней сети. Ранее рабочий вход сохранять на период TTL; выдержать сутки наблюдения за первой публикацией перед расширением. При сбое убрать новое имя из карты и вернуть прежнюю запись; при регрессии VPN снять цепочку целиком.

### Что это исправляет, а что нет

Независимый московский веб-вход устраняет обязательный публичный обход через NL. Он не исправляет медленную авторизацию на любом входе. Отдельная работа платформы БД — добавить наблюдение времени запроса к `pg-critical-rw` по узлам клиента вместе с текущим primary и задержкой подтверждения записей. Во время первого замера primary был на `socrat-5`, и межузловой RTT уже объяснял сотни миллисекунд на один обмен. При повторном осмотре primary был **на `socrat-1`**, а TCP-подключение из домашних реплик заняло 12–18 мс с DNS. Не закреплять Authentik за вчерашним primary и не отключать синхронную репликацию ради одного снимка.

| NL (`109.120.141.60`, `socrat-2`) | [Контроллер на внешнем входе](../../charts/traefik-edge/values.yaml) читает Ingress только из перечисленных пространств имён. При проверке `schoolbot` в списке не было. Общий класс `traefik` сам по себе не делает HOME и NL взаимозаменяемыми. |

Argo CD у одного пользователя открывается медленно, у другого — быстро; для публичного файла RustFS поступила похожая жалоба. **Обходной маршрут — гипотеза, а не диагноз.** Задержка может возникать на DNS, у провайдера, на IPv6, из-за потерь или MTU, при TLS-рукопожатии, входе через Authentik, загрузке ресурсов страницы или чтении из хранилища. Ответ 404 для бота сам по себе не объясняет медленную загрузку двух других сервисов.

### Первый замер: Authentik с Mac, 24 ноября 2026, 16:02–16:10 UTC

После жалобы на зависание после ввода кода проверили две части пути по отдельности. В свежем профиле Chrome под управлением Playwright открывали страницу входа без учётных данных. Через Chrome DevTools Protocol фиксировали фактический IP, HTTP-статус и время до заголовков (`Network.responseReceived`, `timing.receiveHeadersEnd`). Для каждого входа запускали отдельный браузер, подменяя только разрешение имени; сертификат проверялся по обычному имени. По одному открытию на вариант, не процентили. Время относится к отдельному запросу, не ко всей загрузке страницы.

| Вариант | Фактический IP | HTML до заголовков | Начальный GET шага входа до заголовков | Результат |
| --- | --- | ---: | ---: | --- |
| Обычный DNS | `109.173.40.247` | 798 мс | 830 мс | Форма видна |
| HOME | `109.173.40.247` | 329 мс | 585 мс | Форма видна |
| Moscow | `91.189.82.238` | 1500 мс | 847 мс | Форма видна |
| NL | не установлен | — | — | Нет HTTP-ответа за 9 с; две отдельные попытки curl ранее не установили TCP за 3 с каждая |

**Независимое серверное наблюдение:** в 16:03–16:06 UTC реплика Authentik на `socrat-1` зарегистрировала GET обработчика входа за 18,2 с, POST за 28,3 с и POST с редиректом `302` за 169,3 с. В том же интервале проверки готовности трёх реплик истекали в ожидании заголовков; после инцидента при опросе готовы были две из трёх. Эти проверки не проходят через публичный DNS. Принадлежность POST конкретному пользователю не установлена. Успешный GET формы **не** воспроизводит отправку кода, а недоступность NL из одной сети не означает глобального отказа.

**Дополнение к диагностике:** вести две задачи независимо. Для NL повторить TCP/TLS с другой внешней сети и сопоставить с наблюдениями на входе. Для Authentik сопоставить по UTC хвост задержек GET/POST на каждой реплике, изменения готовности, ожидание подключений и запросов к БД, давление ресурсов и сеть между узлом и БД. Разовый `kubectl top` после задержки её причину не показывает. При повторении отделить время ответа POST от времени следующей навигации после `302`; использовать только обезличенные времена и статусы, не сохранять тела запросов или коды. Не считать смену IP исправлением Authentik, пока отдельно не проверен полный вход.

### Argo CD: проверять карточку Pod, а не только страницу входа

24 ноября около 16:12 UTC проверили прямую ссылку на Pod приложения `schoolbot`. В чистом Chrome через HOME документ пришёл за 58 мс до заголовков, но браузер перешёл на `/login`: это замер загрузки оболочки, не карточки. В логах сервера Argo за соседнее 20-минутное окно были отдельные вызовы `ManagedResources` за 13,25 с с результатом `Unauthenticated` (не успешное чтение ресурсов), а также успешные `ListResourceEvents` за 2,29 с, `GetResource` за 1,27 с и `ListResourceActions` за 1,12 с. Это длительности обработки RPC, не доказательство принадлежности запросов конкретной вкладке. Долгоживущие `Watch` и `WatchResourceTree` не считать признаком медленной загрузки по времени закрытия потока.

Для воспроизведения открыть прямую ссылку с обычной авторизованной ролью наблюдателя; отдельно измерить время до появления дерева, сведений о Pod, событий и первого полезного ответа потока. Сопоставить времена REST-запросов в DevTools с соответствующими RPC Argo по времени UTC. Если задержка внутри RPC подтверждается, проверить обращения к Kubernetes API и состояние кэша Argo, прежде чем менять публичный маршрут. Ошибку запуска контейнера учитывать отдельно от времени отрисовки карточки.

### Внутренний путь Authentik → PostgreSQL: контрольный замер 16:29 UTC

Authentik использует `pg-critical-rw`, а не `pg-internal`. В момент проверки primary `pg-critical-2` находился на `socrat-5`, standby — на `socrat-0` и `socrat-1`. Из каждого серверного Pod сделали три TCP-соединения к каждому адресу и пять `SELECT 1` в одном уже открытом соединении с autocommit. Прямой IP primary использован только для диагностики, не для настройки приложения.

| Узел клиента | TCP до primary напрямую | `SELECT 1` через Service | `SELECT 1` напрямую |
| --- | ---: | ---: | ---: |
| `socrat-5` | <1 мс | 0–1 мс | 0–1 мс |
| `socrat-0` | 167–189 мс | 211–274 мс | 142–175 мс |
| `socrat-1` | 187–254 мс | 214–305 мс | 149–185 мс |

TCP между домашними узлами и локальными standby занял 0–3 мс; обратное направление с `socrat-5` до этих standby — 190–241 мс. На `socrat-0` маршрут к Pod primary проходит через VXLAN `flannel.1` с удалённым адресом `10.250.0.41` на `wg-socrat`. Даже ping этого адреса **с хоста**, без Kubernetes Service, Pod и SQL, занял 156–200 мс (4 из 4 ответов). Следовательно, большая задержка воспроизводится ниже приложения и Service, но эти короткие выборки не доказывают потерь или причину задержки конкретного входа. Не складывать времена отдельных диагностических проб как длительность одной авторизации.

До изменения размещения или переключения БД: сравнить RTT и ретрансляции во времени по участкам фактического туннеля с учётом [предыдущей диагностики маршрута](../records/handoffs/wireguard-1-5-router-repair-20261116.md); сопоставить с задержками OIDC по репликам, ожиданиями SQL и подтверждениями синхронной репликации при записях. Повторить тот же контроль для других потребителей, учитывая размещение **их** primary. Устранение публичного обходного маршрута не заменяет эту работу.
