# Three independent public web entrances: diagnosis and rollout plan

**Status: proposed for review, not approved for execution.** Goal: an explicitly published web service is reachable through the designated HOME, Moscow and NL entrances using one Kubernetes route; Moscow web traffic must not need NL. This PR changes no listeners, DNS records, access grants or workloads. A healthy entrance is not a substitute for a reachable application, database, identity provider or volume.

## What we know and what we do not

| Entrance | Evidence and consequence |
| --- | --- |
| HOME (`109.173.40.247`) | A forced-IP HTTP-01 request for `bot.sch1357.ru` previously reached the solver. That was neither a successful bot response nor proof of general availability. |
| Moscow (`91.189.82.238`, `socrat-4`) | The worker runs the host-network [VPN relay](../../charts/vpn-transit/templates/deployment.yaml); its native fallback is a separate potential port owner. The documented Monori HTTPS path relays to NL. A forced Moscow bot challenge redirected to HTTPS and returned 404. This does not prove every Moscow connection takes that path. |
| NL (`109.120.141.60`, `socrat-2`) | The [edge configuration](../../charts/traefik-edge/values.yaml) watches selected namespaces; the observed list omitted `schoolbot`. HOME and NL are not interchangeable merely because both consume the `traefik` class. |

Argo CD is slow for one user and fast for another; the RustFS public-file report is similar. Indirect routing is a hypothesis, **not the diagnosis**. DNS, ISP routing, IPv6, loss/MTU, TLS, authentication, frontend assets, storage or the application itself can produce the same symptom. A 404 on one host does not explain latency on two others.

## 1. Measure before changing routes (network owner + affected users)

- Get a UTC window, ISP/region, resolver, VPN on/off and the affected operation from the reporter. Repeat from their network, one known-fast network, and an independent external probe. Do not collect cookies, tokens, signed URLs or unredacted browser traces.
- From each vantage, compare normal DNS with each forced IP **using the real hostname, SNI and certificate validation**. Record A/AAAA, resolver TTL, actual remote IP, status/redirect chain, DNS/TCP/TLS/TTFB/total time and byte count. Test IPv4 and IPv6 separately where advertised; do not infer IPv6 availability from A records. Repeat at two times of day. Group failures and latency by host, entrance and vantage rather than averaging everything together.
- Use an Argo landing page, one static asset and the normal login flow (tester signs in personally); separate time on the IdP from time on Argo. For RustFS, use a known **public object**, not a bucket listing: check a small range for `206` and expected bytes, then measure a bounded larger transfer. Verify the private console still requires login. Use a stateless canary for schoolbot-style routing until the app has a healthy backend; do not test by sending bot messages.
- Correlate client timestamps with ingress request/upstream durations, backend health and node resource pressure. Compare repeated requests to a small response with the larger transfer. Trace/MTU investigation is warranted if connections stall before HTTP or only large responses stall. Deliver a baseline table with success rates and p50/p95, a reproducible slow case or an explicit inconclusive result. Do not promise a latency fix from the redesign alone.

## 2. Prove the Moscow path and choose its public listener (platform + VPN owners)

Inventory live TCP **and UDP** listeners on Moscow, host networking/NAT, port 80 redirects, TLS termination, SNI/ALPN and fallbacks, protocols used by real supported VPN clients, and which process reclaims ports on restart. Read the [worker decision](../decisions/2026-11-13-keep-moscow-as-a-kubernetes-worker.md) and [Monori exception](../applications/monori/monori-public-entrances.md). Capture redacted before-state, monitoring and the exact restoration procedure. Do not restart the active relay to discover how it works.

Target web path: **client → Moscow public IP → Moscow ingress → Service → ready endpoint**. Prove actual underlay/overlay and return paths to endpoints on `socrat-5` and a HOME node, including payload size, NetworkPolicy and firewall. A Kubernetes Service or WireGuard peer alone does not prove independence: check whether its next hop, tunnel, DNS, API access or TLS material depends on NL. Distinguish serving existing routes during an outage from reconciling new routes.

**Decision gate before implementation:** Prefer a dedicated Moscow web IP/listener if the provider can supply it and the owner accepts the cost; this leaves the current VPN endpoint untouched. If the existing IP must serve both, prototype a single public listener that can dispatch verified web names to a local ingress and preserve existing VPN behavior. Test actual supported clients including non-SNI, unknown-name and non-HTTP cases where applicable. Never assume every VPN client sends ordinary TLS SNI. Keep port 80/HTTP-01 and UDP requirements explicit. Do not bind two controllers to the same address/port or remove the native fallback. If compatibility cannot be demonstrated, use a separate IP or stop. Deliver a listener/port ownership diagram and reviewed rollback before switching traffic.

## 3. One publication contract, not three copies of each route (platform owner)

Use the existing Ingress/Service/TLS Secret as the route source; maintain one reviewed declaration of which hosts/namespaces are public and any entrance exceptions. Inventory existing contracts before choosing the declaration location; do not assume `deploy/public-web/services.json` already lists every route. Generate or validate consistent namespace watches, scoped read RBAC and ingress class selection for each controller. Keep one ingress-status writer and cert-manager as the sole certificate owner. Verify HTTP-01 solver visibility and wildcard/private ingress isolation. Namespace-wide Secret access is a material grant: explicitly review mixed public/private namespaces before onboarding them.

Implementation PRs should separate (a) inventory and offline render tests, (b) Moscow canary/listener, (c) changing existing placements or DNS. Start from [the edge chart](../../charts/traefik-edge/) and [existing public probe](../../scripts/check-public-ingress.py); do not blindly clone NL-specific node/IP/VPN routes. Test that a new declared public host gains the intended entrances, undeclared/private hosts do not, and exclusions (VPN, Monori, protected consoles, Argo-specific protocols) survive. Add the publication step to the developer wiki after acceptance.

## 4. Canary, cutover and DNS (network owner; domain owner for external zones)

1. Deploy a dedicated non-sensitive canary on a spare listener/IP first. Pin requests to each address with DNS unchanged. Verify TLS chain/SNI, expected body, redirects, HTTP-01, large responses, Argo UI/streaming or gRPC if supported, RustFS ranges, unauthorized denial, and existing VPN sessions plus fresh connections. Confirm source-IP/trusted-proxy behavior; do not widen trust to make tests pass.
2. Demonstrate Moscow independence using a **canary-only** route restriction excluding the NL next hop, correlated with Moscow ingress/backend observations. Do not power down NL or disconnect the production mesh. Repeat with an endpoint outside HOME if claiming independence from a HOME outage. Record what still depends on HOME, especially storage/DB. If an equivalent safe test is impossible, mark independence unverified and do not advertise it.
3. Propose thresholds against the phase-1 baseline before cutover: no unexpected TLS/auth/VPN failures, correct bytes and routes on every advertised entrance, and no material p95 regression on the affected networks. Agree on the numerical latency budget with the owner; do not hide a slow vantage in a global median. Run probes for at least 24 hours on the canary before broadening.
4. Publish one approved hostname first, retain the prior working entrance, then expand in batches. For `sch1357.ru`, REG.RU is authoritative: coordinate a host record with its owner, not a zone delegation. Keep schoolbot on its verified entrance until Moscow passes. For operator-owned zones, [authoritative DNS](../network/public-entry/public-dns.md) should publish a consistent **per-host set of healthy entrances**, not the answering NS's own IP. Static multiple A records are not priority failover. Define probe quorum, withdrawal/recovery hysteresis, all-probes-failed behavior and TTL before automating DNS. Preserve existing per-host policies; no blanket wildcard or global DNS migration.

## Stop conditions, rollback and sign-off

Stop on unexpected exposure, wrong certificate, any VPN regression, repeated timeout on a supported vantage or an unverified backend path. Withdraw the canary/new address first; continue serving cached answers for the TTL where safe. Restore the last known listener and VPN port owner through the reviewed playbook, revert only the affected GitOps changes, then recheck old web, DNS and VPN paths independently. No blanket Argo sync or firewall flush. Record before/after measurements, tested failure domains and remaining exceptions in a handoff.

**Requested decisions:** approve measurement scope and a Moscow canary; name the network/VPN and DNS owners; choose dedicated IP vs shared listener after the compatibility report; approve the traffic window, thresholds and first production hostname separately. Merging this plan authorizes none of those production changes.
