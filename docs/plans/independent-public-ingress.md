# Публичный HTTP в Socrat: один маршрут приложения, три входа

**Целевой контракт:** каждая публичная точка — одинаковая реплика CoreDNS и Traefik. Имя площадки — метка инвентаря, а не условие маршрутизации. Из записи экземпляра берём только размещение и собственный публичный IPv4. Один список публичных Ingress определяет одинаковые домены, маршруты и namespace/RBAC всех реплик. Закрытые и зарезервированные имена от этого публичными не становятся.

```text
авторитетный DNS реплики i: A любого обычного веб-имени нашей зоны → публичный IP реплики i
HTTPS на этом IP → Traefik реплики i → тот же Ingress / TLS Secret → Service приложения
```

Все реплики знают одну зону: NS, glue, MX, TXT и статические инфраструктурные записи сохраняются. Различается ответ A для обычного веба, а не набор имён. Внешней зоной школы распоряжается её владелец; это не меняет маршруты Traefik. Публичный CoreDNS авторитетный, не рекурсивный; внутренний кластерный DNS — другой сервис. Цель — не менять production Knot или работающий VPN вместе с рефакторингом.

### На чём основано решение

- На `socrat-4` сейчас один публичный IPv4, TCP 80/443 и UDP 443 заняты. [Конфигурация транзита](../../deploy/vpn-hardening/moscow-transit.json) задаёт для TCP 80/443 фиксированный адрес NL без анализа SNI. Поэтому установка второго процесса на эти же порты не решает задачу.
- С самого `socrat-4` запрос к **ClusterIP** Argo с настоящим SNI и проверкой сертификата вернул `200` за 171 мс (`/api/version`, backend на `socrat-0`). Проверка готовности Authentik через его Service вернула `200` за 105 мс. RTT с Москвы до WG-адреса HOME — 14 мс, до `socrat-5` — 6–16 мс. Для доступа Москвы к сервису не требуется публичный HTTPS-вход NL. Это не испытание отключением NL.
- В момент замера на VPS было около 208 МиБ доступной памяти; Kubernetes показывал около 327 МиБ allocatable **всего**, не свободных. Не резервируем последний запас под второй тяжёлый стек.

### PR 1. Единый список публикаций

`deploy/public-web/entrances.yaml` содержит инвентарь экземпляров и общий каталог публикаций. Настройки отдельных реплик не содержат списков сайтов или namespace. При добавлении публичного имени все реплики получают один и тот же маршрут из Ingress владельца. Права на чтение Secrets пересматриваются **один раз для общего scope**. Смешанный namespace следует разделить до ввода всех реплик, а не молча исключить его на одной площадке. Argo использует одинаковый проверяемый TLS до backend. Выбор приложения для проверки не влияет на содержимое конфигурации.

### PR 2. Один публичный Traefik на Москве; транзит — обычный Kubernetes Service

1. Рендерить одну пару CoreDNS/Traefik для каждого экземпляра; сравнить наборы имён, маршрутов и RBAC. Сначала проверить непубличные копии, затем заменить прежних владельцев по одному. На `socrat-4` требуется дополнительная операция миграции уже занятого сокета VPN — не отдельный веб-контроллер или иной список сайтов. Это один IP: TCP передаёт упорядоченный поток с повторной доставкой, UDP — отдельные датаграммы. TCP/443 и UDP/443 могут одновременно принадлежать одному Traefik. Не переносить под него DNS, SSH или внутренний WireGuard кластера.
2. В `charts/vpn-transit` запустить транзит в сети Pod (`hostNetwork: false`, без `hostPort`), конфигурацию монтировать из Kubernetes, а не с хоста. Добавить ClusterIP Service с именованными TCP/UDP-портами. Убрать привязку исходящего сокета к адресу хоста `10.250.0.40`; сохранить фиксированную VPN-цель и требуемую идентичность исходящего трафика через штатную маршрутизацию/исходящий NAT узла. До переключения подтвердить наблюдаемый в NL адрес и доступ действующих профилей. Не менять ACL в NL на «разрешить всем».
3. Веб TCP/80 и TCP/443 обрабатывают HTTP-маршруты Traefik (включая HTTP-01). Для отдельного имени VPN на общем TCP/443 — `IngressRouteTCP` с точным `HostSNI` и TLS passthrough на Service транзита. Если имя также обслуживает веб-панель или подписки, **весь этот hostname** остаётся на старом VPN-backend за Service: не пытаться делить зашифрованный поток по URL. Выделенные VPN-порты TCP 32053/32083/32084 и UDP 443/32085/32086 получают отдельные entryPoint и маршруты TCP/UDP на тот же Service. На UDP/443 не включать одновременно HTTP/3. На общем TCP/443 не ставить перехватывающий все подключения TCP-маршрут: у Traefik он имеет приоритет над веб-маршрутами. Для VPN-профиля без отличимого SNI на общем порту выпустить профиль на выделенном VPN-порту и перевести клиентов **до** переключения. Аналогично перенести несовместимый сырой TCP с общего порта 80. Не заявлять прозрачную совместимость без такого перехода.
4. **До окна переключения:** оставить действующий вход без изменений. Для каждого поддерживаемого профиля зафиксировать успешное соединение через старый вход и реальный класс ClientHello: ожидаемое SNI, другое имя или отсутствие SNI. Снимать только метаданные согласованных тестовых подключений, без содержимого сессий и клиентских идентификаторов. Повторить тем же клиентом на непубличном входе нового Traefik; подтвердить выбор маршрута по наблюдению на backend и передачей данных, а не только TLS-рукопожатием. При несовпадении перевести профиль на выделенный порт и повторить обе проверки. Не отключать старый вход при непроверенном профиле или дефиците памяти.
5. **Передача портов:** заранее сохранить проверенную ревизию старого Deployment (`hostNetwork: true`), ссылку на доступный образ, конфигурацию и порядок восстановления исходного режима watchdog. До первой проверки владельцев сокетов согласовать окно переподключения, приостановить автоматическую синхронизацию обеих Applications, исключить восстановление их настроек родительским приложением и запуск нативного fallback, дождаться окончания уже запущенных синхронизаций. Не снимать эту блокировку после успешного bind: она действует до завершения приёмки московского входа по PR 3 либо завершения отката. На успешном пути возобновить синхронизацию только с ревизии Git, где единственным публичным владельцем портов объявлен Traefik. Сверить владельцев сокетов с конфигурацией `vpn-tcp` и `vpn-udp` (последняя включает UDP/443); при расхождении устранить его до окна. Остановить прежнего владельца; через `ss -lnt` и `ss -lnu` убедиться, что освобождены **TCP 80, 443, 32053, 32083, 32084 и UDP 443, 32085, 32086**. Только затем передать весь набор московскому Traefik. При неполном bind не продолжать публикацию.
6. **Откат:** до остановки зафиксировать в Git состояние отката: в чарте московской Application выключен публичный workload Traefik (он не рендерится), ни один из переданных публичных портов не объявлен для него через hostPort или Service, а транзит снова объявлен в прежнем режиме hostNetwork. Проверить это на рендере обеих Applications из той ревизии, которую реально отслеживает Argo. На время передачи не допускать автоматического применения обеих затронутых Applications (включая восстановление настроек родительским приложением) и запуска нативного watchdog. Убедиться, что нет активной синхронизации, затем остановить публичный экземпляр Traefik и подтвердить освобождение того же набора TCP/UDP-портов. Применить сохранённую ревизию hostNetwork Deployment вместо версии в сети Pod; ожидать готовности и убедиться, что все прежние сокеты принадлежат транзиту. Подтвердить рабочий TCP- и UDP-профиль, затем возобновить reconciliation на ревизии отката, проверить, что порты остались у транзита, и вернуть прежнюю политику watchdog. Если Kubernetes недоступен, использовать существующий регламент нативного fallback только после fencing конкурирующего владельца. Откат требует переподключения, а не одновременной привязки двух процессов к порту.

### PR 3. Ввод по одному имени, без массового переключения DNS

После передачи портов добавить отдельное тестовое имя. **До изменения DNS** запрос с `--resolve` проверяет HTTP-маршрут в Москве, ожидаемое тело и отказ на закрытом маршруте, но не доступ центра сертификации. **До публикации рабочих имён** разместить для тестового имени единственную публичную A-запись на Москву (без AAAA на другой вход), на весь срок проверки исключить для этого имени HOME и NL из DNS, включая автоматический failover. До создания заказа убедиться, что каждый авторитетный NS и независимые публичные резолверы возвращают для точного имени только `91.189.82.238`, без AAAA и CNAME; при расхождении остановиться. Не подменять резолвер CA: он должен сам попасть на TCP/80 Москвы по публичной записи. Затем запросить новый сертификат cert-manager через HTTP-01. Подтвердить обращение к solver через московский вход, состояние `Certificate Ready` и ответ по HTTPS с проверкой имени и цепочки без подмены DNS. При неудаче отозвать тестовую запись; рабочие имена не менять. Для контрольного backend исключить NL **только в тестовом пути**, подтвердить ответ логами московского ingress и конечного Pod. Одновременно действующий и новый VPN-клиенты должны работать; проверить применяемые TCP/UDP профили, отсутствие подмены IP в политиках доступа и откат передачей портов прежнему транзиту. Невыполнение любого из этих условий блокирует публикацию. Это приёмка нового компонента, который сейчас ещё не развёрнут.

**Schoolbot — исключение из приёмки публичного DNS.** Зоной `sch1357.ru` управляет владелец в REG.RU. У `inform.sch1357.ru` одна A-запись — `109.173.40.247` (`socrat-0`, HOME). При этой конфигурации клиент не получит адрес NL или Москвы после потери HOME. Проверка `ns1.reg.ru` и `ns2.reg.ru` напрямую по UDP и TCP дала одинаковые авторитетные ответы: одна A с TTL 10800 и NOERROR без AAAA. Это наблюдение, не задание на публикацию. `bot.sch1357.ru` зарезервирован и не является псевдонимом. Ни одно из этих имён не входит в публикацию или откат нашей зоны. Для публичного резервирования необходимо отдельное решение владельца.

Закрытый маршрут для Host `inform.sch1357.ru` проверяется независимо. Внутреннее имя `schoolbot.schoolbot.svc.cluster.local` нужно слушателю для соединения с backend **после** получения HTTP-запроса. Проверки этого имени и `/api/health` не проверяют REG.RU, внешнюю доступность при потере HOME или вход пользователя.

Следующими партиями перенести обычные сервисы, сохраняя авторизацию приложений и отдельные транспортные контракты VPN. Для обычных имён нашей зоны все авторитетные CoreDNS публикуют одинаковые имена, но каждый отвечает своим собственным публичным IP. Проверить TCP и UDP 53 принудительно у каждого NS; затем обычное разрешение через внешние резолверы. Потеря двух входов не гарантирует мгновенное восстановление: влияют кеш A и выбор доступного NS. Не вводить реплику в делегацию только на основании внутренней проверки. Если региональная доступность не подтверждена, это ограничение приёмки, а не скрытая индивидуальная таблица веб-маршрутов. Ранее рабочий вход сохранять на период TTL; выдержать сутки наблюдения за первой публикацией перед расширением. При сбое убрать новое имя из публикации и вернуть прежнюю запись; при регрессии VPN выполнить откат портов по шагу 6 и восстановить прежние DNS-записи **каждого уже переведённого имени нашей зоны**. Проверить ответы авторитетных DNS. До истечения TTL часть клиентов продолжит приходить в Москву на прежний транзит; для имён без маршрута в NL доступ у них восстановится только после обновления кэша.

### Что это исправляет, а что нет

Независимый московский веб-вход устраняет обязательный публичный обход через NL. Он не исправляет медленную авторизацию на любом входе. Отдельная работа платформы БД — добавить наблюдение времени запроса к `pg-critical-rw` по узлам клиента вместе с текущим primary и задержкой подтверждения записей. В 16:29 UTC 24 ноября (снимок A, все значения `SELECT 1` в таблице приложения) primary был на `socrat-5`, и межузловой RTT уже объяснял сотни миллисекунд на один обмен. В 18:25 UTC того же дня (снимок Б, только установка TCP-соединения, не повтор SQL-теста) primary был **на `socrat-1`**, а TCP-подключение из домашних реплик заняло 12–18 мс с DNS. Не закреплять Authentik за вчерашним primary и не отключать синхронную репликацию ради одного снимка.

Для Authentik сопоставить по UTC хвост задержек GET/POST на каждой реплике, изменения готовности, ожидание подключений и запросов к БД, давление ресурсов и сеть между узлом и БД. Разовый `kubectl top` после задержки её причину не показывает. При повторении отделить время ответа POST от времени следующей навигации после `302`; использовать только обезличенные времена и статусы, не сохранять тела запросов или коды. Не считать смену IP исправлением Authentik, пока отдельно не проверен полный вход.

### Argo CD: проверять карточку Pod, а не только страницу входа

24 ноября около 16:12 UTC проверили прямую ссылку на Pod приложения `schoolbot`. В чистом Chrome через HOME документ пришёл за 58 мс до заголовков, но браузер перешёл на `/login`: это замер загрузки оболочки, не карточки. В логах сервера Argo за соседнее 20-минутное окно были отдельные вызовы `ManagedResources` за 13,25 с с результатом `Unauthenticated` (не успешное чтение ресурсов), а также успешные `ListResourceEvents` за 2,29 с, `GetResource` за 1,27 с и `ListResourceActions` за 1,12 с. Это длительности обработки RPC, не доказательство принадлежности запросов конкретной вкладке. Долгоживущие `Watch` и `WatchResourceTree` не считать признаком медленной загрузки по времени закрытия потока.

Для воспроизведения открыть прямую ссылку с обычной авторизованной ролью наблюдателя; отдельно измерить время до появления дерева, сведений о Pod, событий и первого полезного ответа потока. Сопоставить времена REST-запросов в DevTools с соответствующими RPC Argo по времени UTC. Если задержка внутри RPC подтверждается, проверить обращения к Kubernetes API и состояние кэша Argo, прежде чем менять публичный маршрут. Ошибку запуска контейнера учитывать отдельно от времени отрисовки карточки.

### Внутренний путь Authentik → PostgreSQL: контрольный замер 16:29 UTC

Authentik использует `pg-critical-rw`, а не `pg-internal`. В момент проверки primary `pg-critical-2` находился на `socrat-5`, standby — на `socrat-0` и `socrat-1`. Из каждого серверного Pod сделали три TCP-соединения к каждому адресу и пять `SELECT 1` в одном уже открытом соединении с autocommit. Прямой IP primary использован только для диагностики, не для настройки приложения.

| --- | ---: | ---: | ---: |
| `socrat-5` | <1 мс | 0–1 мс | 0–1 мс |
| `socrat-0` | 167–189 мс | 211–274 мс | 142–175 мс |
| `socrat-1` | 187–254 мс | 214–305 мс | 149–185 мс |

TCP между домашними узлами и локальными standby занял 0–3 мс; обратное направление с `socrat-5` до этих standby — 190–241 мс. На `socrat-0` маршрут к Pod primary проходит через VXLAN `flannel.1` с удалённым адресом `10.250.0.41` на `wg-socrat`. Следовательно, большая задержка воспроизводится ниже приложения и Service, но эти короткие выборки не доказывают потерь или причину задержки конкретного входа. Не складывать времена отдельных диагностических проб как длительность одной авторизации.

До изменения размещения или переключения БД: сравнить RTT и ретрансляции во времени по участкам фактического туннеля с учётом [предыдущей диагностики маршрута](../records/handoffs/wireguard-1-5-router-repair-20261116.md); сопоставить с задержками OIDC по репликам, ожиданиями SQL и подтверждениями синхронной репликации при записях. Повторить тот же контроль для других потребителей, учитывая размещение **их** primary. Устранение публичного обходного маршрута не заменяет эту работу.

### Закрытая проверка прав на TLS-источники

[Репетиция с одноразовым сертификатом](../records/handoffs/public-entry-named-tls-20261126.md) показала: Traefik принимает и обновляет сертификат через локальный HTTP-провайдер, когда отдельный источник имеет только `get` одного Secret в другом namespace. Это не делает существующий Kubernetes-провайдер совместимым с такими правами. Пустой конфигурации оказалось недостаточно, чтобы подтвердить отзыв ключа. Перед выбором реализации проверить отказ одного имени без ущерба для второго, поведение при потере API и сохранение маршрутов и авторизации. Настоящие ключи для репетиции не брать; закрытый DNS работает отдельно.

В закрытом опыте при недоступном API и при остановке локального HTTP-источника уже работающий Traefik продолжал принимать новые TLS-соединения со старым ключом после ротации. Новый Pod при недоступном API открыл TCP-сокет, но доверенный TLS не заработал до восстановления источника. Для допуска веб-реплики проверять доверенный TLS и ожидаемый HTTP-ответ, а не только сокет. До публичного окна испытать ограничение давности конфигурации на самом входе; оно не должно останавливать VPN. Продакшен-порог по длительности этих коротких опытов не назначать.

Для закрытого источника TLS проверены две валидные пары ключ/сертификат с
недопустимым набором SAN: только чужое имя и разрешённое имя вместе с лишним.
Источник сверял полный набор SAN с разрешением конкретного источника до выдачи
конфигурации. В обоих случаях новые соединения к основному и лишнему имени
отвергались на этапе TLS. Восстановление корректной пары вернуло ожидаемый
сертификат и ответ HTTP без рестарта; 30 из 30 выборочных проверок второго
независимого сертификата и его маршрутов прошли. Проверка размера полного
каталога, нагрузки опроса и промышленной реализации остаётся отдельной.

На всех трёх узлах по очереди проверен синтетический каталог из 35 TLS Secret
и 37 имён. До и после замены последней пары все 37 имён вернули ожидаемый
сертификат и HTTP-маркер. При периоде опроса 30 с и тайм-ауте 25 с новый
сертификат впервые подтверждён через 36,32 с (HOME), 41,55 с (NL) и 36,42 с
(Москва) после записи. Один проход занимал 9,82–20,69 с с намеренной паузой
250 мс между запросами. Это не верхняя граница и не замер трёх одновременных
реплик. Экспериментальное отключение слушателя через 8 с несовместимо даже с
такими успешными проходами; промышленный порог не назначен. При планировании
учесть 105 точечных GET за полный цикл трёх реплик, задержки и размер реальных
цепочек, не предоставляя list/watch на Secret.

В следующем закрытом опыте три реплики одновременно читали один набор из 35
синтетических Secret. За два перекрывающихся раунда выполнены 210 точечных GET
(105 на раунд). Пауза 800 мс на источник ограничивала нагрузку. При интервале
55 с и тайм-ауте 50 с один и тот же новый сертификат подтверждён через 69,82 с
на HOME, 87,32 с в NL и 76,78 с в Москве после записи. Все 37 имён на каждом
узле дали ожидаемый TLS и HTTP до и после ротации; старое доверие отвергнуто.
Между завершениями сканирований наблюдались интервал плюс длительность
следующего прохода, а не ровно 55 с. Эти замеры не определяют SLA отзыва или
порог отключения: отдельно проверить частичный отказ в середине прохода и
влияние на незатронутые источники. Настройки действующего кластера не менялись.

На HOME при закрытом испытании частичного отказа API действительно вернул
403 на один именованный Secret, а позже в том же проходе источник имитировал
локальную ошибку для другого имени. При отмене всего снимка (503) даже уже
отозванное имя продолжало принимать новые TLS-соединения. При публикации
полного непустого снимка без двух недоступных источников оба имени были
отвергнуты на TLS, остальные 35 работали. После снятия только локальной ошибки
восстановилось только её имя; после возврата разрешения — все 37. Следствие:
не терять явный отзыв из-за ошибки другого чтения; временное исключение источника
лишает доступности и рабочий сайт. Для потери связи с самим потребителем или
перезапуска генератора это не доказательство доставки отзыва.

На HOME генератор закрытого стенда после настоящего 403 завершился до выдачи
снимка. Kubernetes перезапустил только его контейнер. Пока генератор не начал
выдавать конфигурацию, два обхода по 37 имён подтвердили прежние сертификаты
и ответы HTTP, включая отозванное имя. После снятия тестовой паузы генератор
повторно прочитал сохранявшийся отказ; через 18,86 с имя отвергалось на TLS,
остальные 36 работали. Возврат точечного разрешения восстановил все 37.
Перезапуск или запись об отказе у источника не равны применению у Traefik.

Для `identity/rustfs-public-reader` подготовлен выключенный по умолчанию
допуск: только Pod контроллера в `public-entry`, только TCP/8080. Он не
предоставляет доступ к прямому S3 (9000) или консоли и не меняет приоритеты.
Его включение само по себе не исправит 502 прямого маршрута с приоритетом
160. До переключения отдельно согласовать владельца этого маршрута и
проверить границы операций с объектами, включая адрес без поддомена RustFS.

**Владелец `/public/` и два разных имени.** У живого Ingress
`rustfs/rustfs-public-files` (приоритет 160) поля `spec.rules` принадлежат
менеджеру `kubectl-patch`, а не Argo. Метки отслеживания и ownerReference нет;
связанная политика `public-files-from-traefik` записана через
`kubectl-client-side-apply`. Их нет в списках ресурсов приложений Argo на момент
проверки. Эти признаки не устанавливают личность владельца и не дают права
удалить ресурсы. Напротив, `identity/rustfs-public-reader` (155) отслеживается
приложением `rustfs`, но описывает только имя `rustfs.socrat.alchemmist.xyz`.
Его Deployment был `OutOfSync`; всё приложение принудительно не синхронизировать.

Один и тот же известный PNG `/public/wiki/rancher-secrets/type-fbebfdb07632.png`
на `socrat.alchemmist.xyz` с проверкой имени TLS: HOME вернул 200 (121274 байта,
ожидаемый префикс SHA-256), а для диапазона — 206 с верной сигнатурой. NL и
Москва вернули 404 для полного GET. Для диапазона Москва вернула 404; в NL
после одного тайм-аута два повтора вернули 404. Это уже расхождение действующих
входов, не тест CNI. На имени с префиксом `rustfs` тот же объект ранее успешно
читался через все три IP. Ответ 404 не устанавливает конкретный backend.

Для закрытой реплики сравнить общий reader на **обоих** именах с контрактом
публичного чтения: точные байты, Range, отсутствие выдачи приватных объектов,
без раскрытия S3 API или изменения остальных путей блога. Имя клиентского Host
не определяет политику бакета. При положительных результатах согласовать
передачу обоих имён в управляемый маршрут, исключить старого владельца из
новой конфигурации явно и подготовить откат. До этого не менять приоритеты,
не добавлять второй бесконтрольный Ingress и не считать изменение #618
исправлением публичного 404.

**Проверка самого reader, отдельно от Ingress.** Оба готовых Pod
`identity/rustfs-public-reader` на `socrat-0` и `socrat-1` проверены через
временный локальный `port-forward`. При обоих клиентских Host один и тот же
PNG из вики дал ожидаемые 121274 байта и префикс SHA-256 (200); диапазон
первых восьми байтов дал точную сигнатуру и `Content-Range` (206). Корень
бакета `/public/` и контрольный путь за пределами него дали 404. Все 16
проверок прошли. Это подтверждает поведение двух backend Pod, а не допуск CNI
нового контроллера, публичный TLS или выбор маршрута.

В отдельном закрытом namespace проверен известный существующий *тестовый*
приватный объект: тот же образ и конфигурация reader, адрес upstream заменён на
локальный имитатор с двумя различимыми объектами. Для обоих Host прямой
контроль к имитатору подтвердил наличие приватного объекта (200); reader
выдал публичный объект (200), а запрос приватного вернул 404 без его байтов.
Внешняя сеть была запрещена, namespace удалён. Это проверяет границу пути
reader, не IAM или ACL боевого бакета. До передачи двух имён нужны закрытая
сквозная проверка через контроллер и согласованный контрольный объект с
заведомо приватными правами; случайный несуществующий ключ его не заменяет.

На всех трёх узлах закрытый Traefik с одинаковой тестовой конфигурацией принял
доверенный TLS только на loopback и дошёл до реальных сервисов. Argo вернул
версию по проверяемому HTTPS, без учётных данных отказал в списке приложений
(401, код 16), а при заведомо неверном имени серверного сертификата версия не
была получена (500). NetBird Management по h2c вернул непустой ответ на
`GetServerKey`; Signal вернул нативную ошибку на несуществующий метод. Это не
проверка Signal-потока, VPN-трафика или входа в Argo. Все тестовые namespace
удалены. Для RustFS отдельно проверить адрес публичного forward-auth при
недоступности двух входов: наличие CRD не доказывает независимость от DNS или
работу авторизации через оставшийся вход.

Закрытая проверка RustFS на HOME, NL и в Москве отделила серверный вызов
forward-auth от браузерного входа. Только внутри тестового Pod имя RustFS
указывало на loopback; исходящая сеть разрешала лишь приватный Authentik.
Везде контрольный маршрут вернул метку (200), путь outpost — 204, защищённый
корень без сессии — перенаправление на авторизацию Authentik без метки. При
отсутствии доверия к тестовому TLS-сертификату вызов завершился 500, метка не
раскрылась. Это проверка серверного вызова, а не полного входа пользователя:
браузеру ещё нужен доступный `auth.socrat.alchemmist.xyz`, а проверка ACL
публичного и приватного объектов остаётся отдельной. Тестовые имена маршрутов
и доверенный тестовый сертификат не переносить на публичные слушатели.

Продолжение анонимного запроса RustFS до HTML входа проверено отдельно: оба
имени (RustFS и Authentik) на каждом шаге направлялись в один и тот же
закрытый Traefik с сохранением SNI и проверкой TLS. На каждом из трёх узлов:
302 с корня RustFS, 302 с адреса авторизации Authentik, затем 200 со страницей
`default-authentication-flow` и компонентом формы Authentik. Учётные данные
не отправлялись. Это не проверка загрузки JS в браузере, завершения OIDC,
обратного вызова или прав на объекты.

Известный публичный PNG из вики проверен полным GET и диапазоном байтов на
всех трёх действующих IP: 200 с ожидаемыми размером и префиксом SHA-256;
206 с правильной сигнатурой PNG и диапазоном. В закрытой проверке на тех же
трёх узлах ситуация другая: при наличии обоих правил выбран прямой маршрут
с приоритетом 160, но он возвращает 502; отдельно выбранный reader тоже
возвращает 502. Это не отказ ACL объекта: проверить допуск Pod контроллера к
реальному endpoint, не открывая доступ всему пространству имён. Проверка
отказа для заведомо приватного объекта остаётся отдельной.

На изолированном Traefik подтверждён риск неявного приоритета. В примере
переписывание Prefix `/public/` в правило по сегментам изменило длину с 46
на 67. Точный маршрут с явным приоритетом 47 из победителя стал проигравшим;
при явном переносе исходного приоритета 46 снова победил. Но `/public` без
завершающей косой черты всё равно перешёл с резервного на другой backend.
Поэтому до переноса отдельно сверять режим сопоставления каждого исходного
контроллера, область действия правил и приоритеты. Ответ 200 от обоих backend
не является доказательством правильного выбора маршрута.

Для существующих маршрутов Monori и Schoolbot подготовлена привязка метки
обнаружения к точному имени из настроек владельца релиза. Подмена имени на
`bot.sch1357.ru` не наследует метку. Рендеры с допуском и без него одинаковы
после удаления единственной метки Ingress; в частности, OIDC Monori, сертификат,
маршрут, образ и настройки БД Schoolbot не меняются. Перед выводом о готовности
отдельно проверить применённую метку, TLS `inform.sch1357.ru` и возврат ответа
реального приложения. Делегирование `sch1357.ru` и зарезервированное имя вне
этих изменений; для Monori остаётся региональная проверка доступности.

### Отдельный контракт временного маршрута HTTP-01

В `ansible/playbooks/k3s.yml` закреплён cert-manager `v1.16.2`. В исходниках
этой версии [Ingress](https://github.com/cert-manager/cert-manager/blob/v1.16.2/pkg/issuer/acme/http/ingress.go)
для отдельного решателя содержит путь с типом `ImplementationSpecific`, а
[Service](https://github.com/cert-manager/cert-manager/blob/v1.16.2/pkg/issuer/acme/http/service.go)
по умолчанию имеет тип `NodePort`, если он не переопределён в конфигурации
эмитента. Ingress, Service и [Pod](https://github.com/cert-manager/cert-manager/blob/v1.16.2/pkg/issuer/acme/http/pod.go)
привязаны к `Challenge` через ссылку на владельца-контроллер. Это проверка
исходников закреплённой версии, **не** наблюдение текущего кластера. Метка
обнаружения из шаблона эмитента сама по себе не делает временный Ingress
обычным HTTPS-маршрутом и не разрешает чтение какого-либо ключа.

- Не ослаблять общий компилятор путей и не включать все `NodePort` ради
  решателя. Для закрытого опыта использовать отдельную ветку только на HTTP:
  одобренное точное имя, активная задача HTTP-01 и точный полный путь её
  токена. Не открывать весь префикс, общий порт узла или произвольный backend.
- Сверять пространство имён и действующий UID `Challenge` для Ingress,
  Service и Pod; дополнительно проверять порт, готовность и фактическую цель
  EndpointSlice. Отдельно подтвердить доверие к авторам объектов: совпадение
  меток или ссылок на владельца не доказывает полномочия записавшего их.
- На каждой закрытой реплике проверить точный ответ на GET, затем другое имя,
  соседний токен, продолжение пути, подменённый UID, удаление задачи и повторное
  создание с тем же именем. Критерий отказа — запрос не получает ответ решателя;
  обычное приложение может иметь собственный обработчик для этого пути.
  Не писать токен и тело ответа в отчёт. Удаление задачи не должно снимать
  обычный HTTPS-маршрут приложения, а отсутствие его ключа не должно блокировать
  HTTP-проверку получения первого сертификата.
- Только после закрытой проверки отдельно согласовать внешнее тестовое имя,
  проверку центра сертификации и откат. Ни успешный прямой GET, ни чтение
  исходников не подтверждают публичный выпуск или продление сертификата.

**Первый закрытый опыт с настоящим решателем.** Без сетевого выхода, DNS,
центра сертификации и Kubernetes запущены закреплённый Traefik и настоящий
`cert-manager-acmesolver` версии `v1.16.2` (использованный digest
`sha256:6ea8176c5baa6a7f6b1262ac7b51f5888006b4c57ec574b708e3bc11c8fe441c`).
Проверялось синтетическое имя `.invalid`, только HTTP на loopback. Отдельный
обычный обработчик того же имени отдавал фиксированный маркер. В каждой из
трёх стадий — до предъявления, во время него и после снятия — сделано пять
проверок новыми соединениями. Лишь точный Host и полный путь во второй стадии
вернули `200` с точным ожидаемым телом решателя. При другом Host тот же путь
дал `404`. Соседний токен, продолжение пути и `/` вернули обычный маркер на
всех стадиях. После снятия правила точный путь снова вернул обычный маркер,
**хотя процесс решателя продолжал работать**. Ключ сайта для опыта не нужен;
значения токена и ответа не сохранялись в журналах или отчёте.

Это 15 проверок обработки запросов и смены конфигурации одного изолированного
слушателя, а не выпуск или продление. Правило переключалось вручную в файловом
провайдере: проверка реального UID `Challenge`, владения Ingress/Service/Pod,
удаления и пересоздания объектов, доступности на трёх узлах и наблюдения со
стороны центра сертификации ещё впереди. Политика обычных Ingress не менялась.

**Проверка поколения задачи HTTP-01.** Изолированная проверка
`ci/quality/public_http01_generation.py` принимает отдельно ожидаемые
пространство имён, имя задачи, UID и имя сайта. Она сопоставляет активную
предъявленную задачу и ссылки на неё как на владельца-контроллер сразу у
Ingress, Service и Pod. Проверяет точный единственный путь, имя Service и
порт 8089 в Ingress. Возвращает только да/нет; это не разрешение публиковать
маршрут. Отсутствующая или удаляемая задача не подходит. Пересоздание с тем
же именем и токеном, но новым UID не делает старый Pod допустимым.

В изолированном опыте настоящий решатель оставался доступен на loopback,
а наблюдения объектов и UID были синтетическими. Решение проверки управляло
включением точного правила. Четыре стадии: исходная задача — точный ответ;
задача отсутствует — обычный обработчик; новая задача со старым Pod — обычный
обработчик; все ссылки относятся к новому UID — точный ответ восстановлен.
На каждой стадии выполнены пять GET с контролем имени и соседних путей.
Это не наблюдение событий API и не измерение задержки снятия в кластере.
Остаются проверка фактического EndpointSlice и порта назначения, полномочий
авторов, полноты и свежести снимка, опыт на трёх узлах и отдельное согласование
публичного тестового выпуска. Настройки эмитента не применялись.

Следующая ступень закрытого компилятора возвращает только проверенный адрес
Pod решателя. После проверки поколения она сверяет три метки cert-manager
`v1.16.2` (контрольные суммы имени и токена не являются авторизацией), селектор
Service, его UID в ссылке владельца EndpointSlice, ссылку цели на конкретный
Pod, IP в пределах разрешённой сети Pod, готовность и TCP/8089. Для этого
узкого случая нужен один непротиворечивый IPv4 EndpointSlice с одним адресом.
Неоднозначность означает отсутствие назначения. Даже для типового Service
`NodePort` компилятор **не** возвращает порт узла или ClusterIP. Обычные
HTTP-backend по-прежнему требуют Service типа `ClusterIP`. Это проверено на
синтетических объектах; доверие к авторам, живая согласованность снимка и
прохождение запроса через три узла отдельно не установлены.

**Закрытый опыт с настоящим EndpointSlice на трёх узлах.** В одноразовом
пространстве работали один HTTP-маркер и три контроллера без токенов API,
с TCP-слушателями только на loopback Pod. Вход и выход ограничены метками
внутри этого пространства и TCP/8089. Использованы реальные ClusterIP Service,
Pod и созданный контроллером Kubernetes EndpointSlice. `Challenge`, Ingress и
ссылки на владельца-задачу для Service и Pod подставлялись **только в памяти**:
задача не отправлялась в cert-manager, поддельные ссылки в кластер не писались.
Backend здесь — маркер с точной проверкой Host/пути, а не сам `acmesolver`.

На HOME, NL и в Москве один и тот же в течение опыта Pod контроллера прошёл
три стадии. Текущий срез дал точный ответ маркера. После пересоздания backend
с тем же именем, но другим UID, сохранённый старый срез и новый Pod не дали
назначения: после применения конфигурации точный путь вернул 404. Новый срез
и новый Pod восстановили точный ответ. На каждой стадии неверные Host и путь
возвращали 404. Итого 27 проверок новыми соединениями в успешном прогоне.

При подготовке опыта обнаружена отдельная ошибка снятия: YAML с непустым
служебным маршрутом, но с явным `http.services: {}`, был отвергнут файловым
провайдером Traefik. Файл уже совпадал с ожидаемым, однако HOME продолжал
обрабатывать прежний маршрут и отдавал 502. Это **не** подтверждение снятия.
В успешном прогоне секция `services` при отсутствии backend опускалась, а
служебный маршрут ссылался на `noop@internal`. Доказательством был ответ
слушателя, не запись файла или результат функции. Этот опыт не доказывает
выпуск, продление, доверие к авторам объектов или предельную задержку отзыва.

Повторный прогон на трёх узлах использовал уже результат функции
`closed_solver_snapshot`, а не ручную сборку YAML в опыте. Она принимает
наблюдения для **одной** задачи и строит конфигурацию отдельного закрытого
HTTP-слушателя: при подтверждённом назначении — точные Host/Path, при
снятии — только служебный маршрут без пустой секции `services`. Для пути
проверки явно выключены журнал доступа и трассировка. Повторены все 27
проверок с реальным пересозданием Pod маркера и живым EndpointSlice. Такой
снимок не должен заменять конфигурацию общего провайдера с другими задачами
или приложениями. Атомарное объединение нескольких задач, ограничения срока
действия снимка и подтверждение выпуска этим опытом не проверялись.

**Две задачи одного имени вместе с обычным HTTP-маршрутом.** Для отдельного
файла решателей `closed_solver_batch` строит снимок полного наблюдения, с
разными именами маршрутов и сервисов для разных UID. Неоднозначные UID,
имена задач в одном пространстве или пары Host/токен не выбирают победителя
по порядку списка, даже если у одного претендента backend уже недействителен.
Пустой набор оставляет непустое служебное правило без секции `services`.
Файл обычного приложения не является входом и не переписывается.

На изолированной внутренней сети Docker, без опубликованных портов, работали
два настоящих решателя `v1.16.2` с разными тестовыми ответами для одного
`.invalid`-имени. Адреса backend были реальными адресами контейнеров, объекты
Kubernetes — синтетическими. Сначала оба точных пути дали собственные ответы.
При устаревшей ссылке на первый Pod его путь вернулся к обычному обработчику,
а второй продолжил давать свой ответ. После снятия обеих задач оба пути дали
обычный ответ; восстановление вернуло оба ответа решателей. На каждой стадии
проверены также обычный `/`, соседний путь и чужой Host: 20 проверок после
сходимости, содержимое файла обычного маршрута не менялось. Контейнеры и
тестовая сеть удалены. Это не непрерывный замер в момент перезагрузки, не
проверка всех приоритетов боевых маршрутов и не разрешение считать неполный
скан пустым. Доступ центра сертификации и продление остаются непроверенными.

**Пустой список или прерванный опрос.** Для отдельного пространства имён
`scan_namespace` начинает чтение без курсора и собирает страницы `ChallengeList`
только одного `resourceVersion` до страницы без продолжения. Пустая страница
с продолжением не означает отсутствие задач. Только затем для разрешённых
имён запрашиваются дочерние наблюдения и собирается файл. Ошибка доступа,
истёкший курсор (`410`), смена версии, повтор UID/имени, зацикливание или
прерывание чтения дочерних объектов не дают **никакого** снимка, а не пустой
файл для снятия маршрутов. Настоящий пустой ответ API с `limit=1` проверен в
одноразовом пустом пространстве: получен только служебный маршрут без чтения
дочерних объектов. Для ошибок и многостраничного чтения использованы тестовые
ответы; настоящие задачи для этого не создавались.

Это не транзакция для Ingress/Service/Pod/EndpointSlice и не ограничитель
устаревания: если новый снимок не получен, ранее предъявленный ответ ещё
может обслуживаться. Читатель должен ограничивать время и размер ответов,
не превращать ошибку API в отсутствие объекта, а снятие по истечении срока
должно проверяться на самом слушателе независимо от успеха следующего опроса.

### Периодические 504 на закрытом пути Schoolbot

После добавления Remark42 повторили проверку без переключения маршрутов. Команда
`uv run python -m ci.quality.closed_schoolbot_samples` делает из каждого постоянного
Pod четыре независимых анонимных запроса `/api/health`: через локальный Traefik,
по имени Service, по ClusterIP и напрямую к проверенному готовому Pod. Каждый раунд
сопоставляет UID Service, источников и назначения. Нужен операторский `pods/exec`,
новых прав слушателям не выдаём. Команда не меняет кластер и не выводит тела ответов.

За 12 раундов (121 с, backend на `socrat-1`) московский слушатель вернул один
`504`, остальные 143 запроса вернули ожидаемый JSON. В отдельном namespace на
тех же трёх узлах сравнили обычное имя upstream и абсолютное имя с конечной точкой
при `ndots:5`: по 36 успешных запросов на каждый из шести путей. Это не доказательство
проблемы DNS или её устранения. Даже одновременные запросы идут по разным соединениям;
успех прямого обращения не исключает краткую потерю пакета на другом соединении.
Не увеличиваем таймауты, не закрепляем IP Pod и не считаем эти серии доказательством
непрерывности. При повторе сопоставить раунд с задержками DNS и соединения на том же узле.

В следующей репетиции временный Traefik с отладочным журналом обслуживал только
`/api/health` через loopback. Отдельный процесс в том же Pod замерял фазы DNS,
TCP и получения заголовков (`ci/quality/schoolbot_phase_probe.py`); его соединение
не является соединением Traefik. Из 36 запросов к московскому слушателю четыре
вернули `504` через 3,00–3,01 с. До внесения отказов журнал этого экземпляра дал
четыре ошибки `lookup … i/o timeout`. В тех же раундах параллельный запрос по имени
тратил на DNS 2,64–2,84 с, а TCP к числовому ClusterIP устанавливался за 14–38 мс.
Все 108 прямых запросов по ClusterIP прошли. При запрете только DNS числовой путь
остался рабочим, а слушатели дали `504` на всех трёх узлах. При запрете только
доступа к backend DNS работал, TCP не устанавливался, слушатели дали `502`.
После снятия обоих ограничений проверки прошли. Рабочие политики не меняли.

Это указывает на фазу разрешения имени **для воспроизведённых ошибок временного
слушателя**, но не устанавливает причину потери или задержки DNS-пакета. В отдельной
парной серии даже имя с конечной точкой получило четыре `504` в Москве; серия не
завершилась до внешнего таймаута, поэтому доли успеха по ней не считаем. Оба временных
namespace удалены. Простую замену имени или увеличение общего таймаута не выкатываем.
Следующий узкий тест — сопоставить время ответа DNS по UDP и TCP через Service
и напрямую через каждый проверенный endpoint CoreDNS, отдельно от времени обработки HTTP.

Для этой проверки запросили абсолютное имя Service Schoolbot напрямую по DNS,
без HTTP, поисковых суффиксов и повторных попыток. Временные Pod на HOME, NL и
в Москве имели только DNS-egress. Для каждого источника сделали по 32 запроса A
и 32 AAAA по каждому протоколу к ClusterIP `kube-dns` и к каждому из двух готовых
Pod CoreDNS (`socrat-0`, `socrat-1`). Сверили владельца EndpointSlice, UID и IP Pod,
порт, протокол и метки. Ожидали A, равный текущему ClusterIP Schoolbot, и NOERROR
без AAAA. Таблица показывает число запросов без ответа за 3 с **из 64**:

| Источник | UDP: Service / `socrat-0` / `socrat-1` | TCP: Service / `socrat-0` / `socrat-1` |
| --- | --- | --- |
| HOME | 0 / 0 / 0 | 0 / 0 / 0 |
| NL | 1 / 0 / 0 | 0 / 0 / 0 |
| Москва | 1 / 4 / 1 | 0 / 0 / 0 |

Все остальные ответы соответствовали ожиданиям. В Москве TCP тоже не всегда был
быстрым: три измерения заняли более секунды, максимум 1,054 с. Таймаут UDP
воспроизвёлся и напрямую к каждому Pod — это не эффект исключительно ClusterIP.
Однако клиентский дедлайн не показывает, потерян ли запрос, задержан ответ или
сработала очередь. Эта серия не доказывает отказ конкретного узла или необходимость
переключить DNS всего кластера на TCP. Временный namespace удалён.

### Публичный DNS при нативном режиме NL: наблюдение до передачи портов

`uv run python -m ci.quality.public_dns_snapshot` обращается без рекурсии к трём
публичным IPv4 из инвентаря на порту 53, отдельно по UDP и TCP. Это не запрос
к закрытым `authority-*-probe`. В отчёте `null` — ответ не подтверждён, `[]`
— проверенный пустой набор адресов. Внешний Schoolbot и выделенное имя VPN не
опрашиваются. Код возврата 0 требует собственный A и отсутствие AAAA для каждого
проверенного имени; это сравнение с целевой формой ответа, не разрешение менять DNS.

Пока `socrat-2` оставался `Ready=Unknown`, во второй серии получены 432 авторитетных
ответа: 36 имён × три IP × два протокола × A/AAAA. На каждом IP для 33 имён вернулись
адреса HOME **и** NL, для `auth.socrat.alchemmist.xyz`, `lms.alchemmist.xyz` и
`monori.alchemmist.xyz` — только HOME. Все ответы AAAA были NOERROR без адресов.
В первой серии один ответ AAAA по UDP на NL не удалось подтвердить. В обеих сериях
итоговый код — 1. В частности, клиент Venice по обычному DNS может получить NL,
где в это время HTTPS для Venice не прошёл. Успех DNS на московском IP не означает,
что ответил независимый московский процесс: прямой запрос не различает локальное
обслуживание и пересылку. Наблюдение не меняет политику Monori и не подтверждает
доступность приложений, цепочку делегирования или выживание при потере двух узлов.

Для двух контрольных маршрутов команда `uv run python -m ci.quality.public_advertised_routes`
сопоставляет опубликованный набор адресов с ответом приложения. Проверка читает A и
AAAA у трёх публичных IP по UDP и TCP, делает новый HTTPS-запрос с проверкой имени
на каждом **инвентарном** IP, затем повторяет DNS-чтение. Адрес из ответа DNS сам
по себе не становится разрешённой целью запроса. Для `www` нужен `200` и заголовок
страницы блога; для `/v1/models` Venice — штатный анонимный `401` с ожидаемой
ошибкой JSON. Секреты, модельные запросы и изменение публикации не нужны.

В замере во время нативного режима NL оба набора DNS совпали до и после проверки:
для обоих имён все авторитетные адреса вернули HOME и NL. HOME прошёл обе проверки,
NL не завершил TLS. Поэтому ни один из 12 случаев «авторитетный IP × транспорт × имя»
не прошёл целиком. Москва также не завершила TLS, но её A не публиковали, поэтому
она не была причиной отрицательного результата. Это не доля неудачных клиентских
запросов: выбор IP, повторные подключения и кеш клиента в проверке не моделируются.

### Установленный генератор и репетиция изменения только `www`

На `socrat-0/1/2/4` без запуска обновления сверены SHA-256 установленных файлов.

Для обычных имён эта версия проверяет TCP/443; проверка TLS Monori отдельная.
Успех TCP при отказе TLS не означает доступность блога или Venice.

Для каждого узла получили только serial и хеш из одного чтения файла зоны.

AAAA остался пустым, A Venice и Monori и MX вершины зоны не изменились. Два ранних
прогона через port-forward не завершились; полный прогон использовал клиент в том же

доступность и не разрешение публиковать `www`, пока HTTPS на NL и Москве не подтверждён.

### Транспорт DNS для поиска backend закрытым слушателем

Проверили гипотезу с TCP без перенастройки кластерного CoreDNS или публичных NS.
Параметр чарта `closed-health` `useTcpResolver: true` добавляет только `use-vc`
в настройки резолвера Pod. По умолчанию опция отсутствует. Это **не** переключение
пользовательского DNS на TCP и **не** автоматический переход с одного транспорта
на другой. При включении параметр затронул бы все разрешения имён в Pod.

Временные слушатели на HOME и Москве запрашивали HTML `www` через реальный Service
блога. Для этой репетиции отключили повторное использование upstream-соединений;
ограничения исходящего DNS накладывали только на временные Pod. Каждую фазу
начинали с новых Pod. При разрешённых UDP и TCP на каждой площадке оба варианта
вернули блог 32/32. Когда оставили только TCP/53, штатный вариант вернул `504` 4/4,
а `use-vc` вернул блог 4/4. При разрешении только UDP/53 результаты поменялись
местами. После восстановления обоих протоколов каждый вариант прошёл 8/8 на каждой
площадке. Namespace удалён. Эксперимент подтверждает выбор транспорта реальным
Traefik, но не преимущество TCP при обычной нагрузке: в исходной серии сбоев не было.
NL не участвовал. Не включать параметр постоянно на основании этой серии.

### Связь выданного сертификата с ответом слушателя без чтения ключа

`uv run python -m ci.quality.public_issued_leaf wiki` и вариант `www` сравнивают
сертификат на публичном сокете с `status.certificate` актуального CertificateRequest.
Проверка ограничена двумя явно заданными владельцами и использует контекст `Socrat`.
Она сверяет Git-привязку, Ready для текущего поколения Certificate, ревизию,
управляющую ссылку по UID, issuer, состояния Approved/Ready, подпись CSR, совпадение
открытых ключей, точный набор DNS SAN и сроки действия листового сертификата.
До и после новых TLS-соединений сверяются UID и resourceVersion обоих объектов.
Если привязки нет или она изменилась, зачёта слушателям нет. Объекты Secret не
запрашиваются; материалы сертификата, CSR и имена запросивших субъектов не выводятся.

Для Wiki ревизия 1 дала совпадение с доверенным листовым сертификатом на публичном
HOME. На NL и Москве TLS не завершился. Для блога Certificate был Ready, но у него
не было `status.revision`, и в namespace `blog` не наблюдалось CertificateRequest.
Поэтому прежний успешный HTTPS на HOME и на частном московском входе не выдаём за
совпадение с подтверждённой текущей выдачей. Отсутствие этой связи не доказывает
недействительность сертификата и не требует принудительного перевыпуска. Ни Approved
на запросе, ни совпадение байтов на сокете не являются разрешением доверять всем,
кто может записать `tls.key`, или переносить ключ на новую площадку.

В закрытой репетиции связали проверенную выдачу с содержимым читаемого TLS-источника.
До именованного GET требуется независимый допуск записывающих субъектов для точного
источника, UID Certificate и набора имён. Выдача сама не создаёт допуск. После GET
отпечаток выбранного листа должен совпасть с выданным, а повторное наблюдение
Certificate и CertificateRequest — с первоначальными UID и версиями объектов.

На временном loopback Traefik в Москве проверили два синтетических источника и три
имени с одноразовым CA. Валидная новая пара с теми же SAN до обновления выдачи
дала строгий отказ SNI для обоих имён источника; соседний источник продолжил
проходить TLS. После согласования выдачи прошли все три имени. Смена версии запроса
между чтениями снова сняла оба имени. Без обоих допусков не было ни одного GET,
и все три имени получили строгий отказ; восстановление вернуло три совпадения.
Первый прогон с файлом `routes.json` дал недоверенный лист, а не успешное применение;
результаты получены после повторения с `routes.yaml`. Материал синтетический, GET и
наблюдения выдачи имитировались; проверка клиента — реальные новые TLS-соединения.
Это не утверждение о доверии к production writer и не rollout. Namespace удалены.

Затем повторили проверку на `socrat-4` с настоящими объектами cert-manager в
одноразовом namespace Socrat: отдельный локальный Issuer/CA, два Certificate,
их CertificateRequest и два именованных TLS Secret. Доверие клиента — только
проверка с добавленным тестовым CA, не публичная цепочка. Оператор читал
публичные объекты выдачи; два разрешённых GET ключей выполнялись с impersonation
тестового ServiceAccount. Для него GET корневого Secret, list и watch Secrets
запрещены. У loopback Traefik не было токена, Service или hostPort.

Без отдельного допуска: 0 GET, 3 строгих отказа SNI. С допуском: 3 совпадения.
Изменили размер EC-ключа первого **тестового** Certificate после GET, дождались
другого выданного листа до повторной проверки: оба его имени получили строгий
отказ, соседнее имя прошло. Следующий цикл вернул 3 совпадения, с новым
отпечатком только у первого источника. Удаление одного RoleBinding дало 403 и
те же два отказа; восстановление вернуло три совпадения. Это наблюдения после
публикации тестового файла, не непрерывная гарантия отзыва старого ключа.
Namespace удалён. Публичный Issuer/ACME, авторизация реальных writers, раздача
ключей между площадками и отказоустойчивость публичных входов так не проверены.

Для блога `python -m ci.quality.blog_validity_baseline` отделяет хронологию
от доказательства выдачи. Повторное чтение в Socrat подтвердило текущий UID
Ingress-владельца, точные TLS-имена, Ready для текущего поколения, отсутствие
`status.revision` и запросов в namespace. Два свежих проверенных соединения
на HOME с SNI `www` получили один и тот же лист, и обе даты его действия
совпали со статусом Certificate. Начало действия — 12 октября, создание
нынешнего Certificate — 1 ноября; указанное время планового обновления —
11 декабря 2026 UTC. Это совместимо с использованием ранее выданного листа,
но не устанавливает кем, как и куда были доставлены ключи или почему нет
CertificateRequest. Не запускать принудительную выдачу для заполнения пробела.

Проверка DNS и приложения для Monori (`public_advertised_routes`) учитывает
разные роли NL: запрашивает там авторитетный DNS, но не рассматривает NL как
HTTP-адрес для этого имени. До и после пробы все три DNS-адреса по UDP и TCP
вернули только HOME в A, пустой AAAA. На HOME через публичный доверенный TLS
анонимный `GET /api/auth/me` дал ожидаемое `401 {"detail":"Not authenticated"}`.
На разрешённом политикой, но не объявленном для Monori московском адресе TLS
оборвался до HTTP. Таким образом, опубликованный путь прошёл проверку,
но географического резерва она не показала. Для `www` и Venice в том же замере
не все опубликованные пути прошли проверку. DNS, маршруты и ключи не менялись.

Уточнение цели: Monori — такой же обязательный маршрут на **всех трёх**
входах. Ограничение HOME/Москва относится к старому публичному генератору DNS,
не к целевой архитектуре. Историческая проверка, пропустившая HTTPS Monori на
NL, этот вход не проверяла. Приватный NL A Monori → NL правилен; его не менять.
После возврата `socrat-2` (`Ready=True`) один tokenless Pod с ограниченным DNS
egress получил все 216 авторитетных self-IP ответов (36 имён × 3 адреса × UDP/TCP),
включая Monori на NL. Pod и политика удалены. Публичный HTTPS с настоящим SNI:
на каждом из трёх IP совпали блог `www` и штатные анонимные 401 Monori и Venice.
В первом замере не подтверждён один публичный UDP A Venice, во втором все 18
сочетаний имя/authority/протокол были стабильны. Это не self-IP публичной зоны
и не доказательство независимого завершения публичного TLS в каждом регионе.

`public_advertised_routes` теперь завершает проверку успешно только при
совпадении **обоих** условий для выбранных имён: прямые HTTPS-проверки прошли
на всех трёх IP и каждый опрошенный авторитетный адрес до/после вернул только
свой A и пустой AAAA по UDP и TCP. Отдельный вердикт для объявленных путей
сохранён. В серии для `www`, Venice, Monori и Wiki прошли все 12 прямых HTTPS
и все объявленные пути, но **0/24** сочетаний имя/authority/протокол выполнили
self-IP. У Wiki `/api/auth/me` на всех адресах показал анонимного пользователя,
без права записи и без необходимости bootstrap. Независимый `public_issued_leaf
wiki` сопоставил текущую выдачу с доверенным листом на всех трёх IP. Это не
разрешение передавать ключи и не доказательство местного TLS или работы при
потере двух других площадок. Публичная зона осталась без изменений.

Для `www` проверен домен возобновления TLS 1.2, а не просто одинаковый лист.
`python -m ci.quality.blog_tls_path` получает анонимный сеанс с настоящим SNI
и доверием CA и пробует возобновить его при новом HTTPS GET к ограниченному
набору кандидатов. Материал сеанса остаётся только в памяти, в выводе — лишь
результаты. У четырёх кандидатов (Pod `socrat-0/1/4`, **сокет узла** `socrat-2`
через SSH loopback) каждый собственный контроль возобновился, 12 перекрёстных
потребовали полного handshake. В двух сериях сеансы с публичных NL **и Москвы**
возобновились на сокете NL, но не на приватном московском Pod. С HOME в этих
образцах возобновился сеанс на `socrat-1`. Это положительная корреляция общей
TLS session state, не уникальная идентификация процесса, не постоянный маршрут
и не физическое отключение. При пересылке или совместном использовании ticket
keys удалённый адрес может выглядеть так же. Зелёный публичный HTTPS Москвы
не засчитывать как самостоятельное завершение TLS. Изменений слушателей нет.

Для публичного `www` на московском IP прослежен и транспортный участок, а не
только TLS resumption. `python -m ci.quality.moscow_blog_relay` связывает cgroup
сокета TCP/443 с Ready hostNetwork relay Pod либо проверенной native unit,
сверяет на узле SHA-256 публичного `user.json` с Git и маршрут до NL через
`wg-socrat`. В успешной серии владельцем был Pod. При открытии HTTPS через
Москву у этого владельца появился ровно один новый поток до `10.250.0.2:443`,
на котором обе разности TCP bytes_acked совпали с длинами двух отдельных
записей нашего TLS-запроса. Блог вернул ожидаемый 200; аналогичный запрос к
HOME не дал такого совпадения. Это свидетельство **зависимости от NL для этой
московской выборки**, не проверка отказа NL, не гарантия постоянного владельца
и не тест пользовательского VPN. Без pcap, чтения ключей, изменений unit,
нативного fallback или публичных портов.
