# Три независимых веб-входа: диагностика и план внедрения

**Статус: предложение для ревью, не разрешение на работы в продакшене.** Цель — публиковать маршрут сервиса Kubernetes один раз и обслуживать его через выбранные входы HOME, Moscow и NL. Для обычного веб-трафика через Москву Нидерланды не должны быть обязательным звеном. Исправный вход не заменяет работающие приложение, БД, хранилище и сервис авторизации.

## Что известно, а что пока только гипотеза

| Вход | Наблюдение и его границы |
| --- | --- |
| HOME (`109.173.40.247`) | Запрос HTTP-01 для `bot.sch1357.ru`, отправленный напрямую на IP с правильным именем хоста, достиг обработчика cert-manager. Это не проверка самого бота и не доказательство постоянной доступности. |
| Moscow (`91.189.82.238`, `socrat-4`) | На узле работает [VPN-транзит](../../charts/vpn-transit/templates/deployment.yaml) в сети хоста. При переключении на резерв порт может занять системная служба. Для Monori задокументирован путь HTTPS через NL. Для бота запрос проверки сертификата через Москву получил редирект, затем 404. Это не доказывает, что любой трафик из Москвы идёт через NL. |
| NL (`109.120.141.60`, `socrat-2`) | [Контроллер на внешнем входе](../../charts/traefik-edge/values.yaml) читает Ingress только из перечисленных пространств имён. При проверке `schoolbot` в списке не было. Общий класс `traefik` сам по себе не делает HOME и NL взаимозаменяемыми. |

Argo CD у одного пользователя открывается медленно, у другого — быстро; для публичного файла RustFS поступила похожая жалоба. **Обходной маршрут — гипотеза, а не диагноз.** Задержка может возникать на DNS, у провайдера, на IPv6, из-за потерь или MTU, при TLS-рукопожатии, входе через Authentik, загрузке ресурсов страницы или чтении из хранилища. Ответ 404 для бота сам по себе не объясняет медленную загрузку двух других сервисов.

## 1. Измерить задержку до изменения маршрутов

**Ответственные:** оператор сети и пользователи, у которых воспроизводится проблема.

1. Записать время в UTC, сеть и регион, DNS-резолвер, состояние VPN и точную операцию. Повторить её из проблемной сети, из заведомо быстрой и с независимой внешней точки. Не собирать cookie, токены, подписанные URL и неочищенные трассировки браузера.
2. Из каждой сети сравнить обычное разрешение DNS с запросом на каждый IP с настоящим именем хоста, SNI и проверкой сертификата. Снять A/AAAA и TTL, фактический IP соединения, HTTP-статусы и редиректы, время DNS, TCP, TLS, до первого байта и до окончания передачи, а также число байтов. IPv4 и IPv6 измерять отдельно, если адреса опубликованы. Повторить в два разных времени суток.
3. Для Argo CD отдельно проверить страницу входа, один статический ресурс и обычный вход пользователя: не приписывать задержку Authentik самому Argo. Для RustFS взять **известный публичный файл**, а не каталог бакета: получить небольшой диапазон с ответом `206`, проверить байты, затем измерить передачу большего, но ограниченного объёма. Закрытая консоль по-прежнему должна требовать вход. Пока у schoolbot нет исправного backend, маршрутизацию проверять тестовым сервисом без состояния, не отправкой сообщений боту.
4. Сопоставить время запросов с длительностью обработки на ingress и backend, состоянием приложения и нагрузкой узлов. Если задержка возникает до HTTP или только на больших ответах, отдельно проверить маршрут и MTU.

**Результат этапа:** таблица долей успеха и задержек p50/p95 по каждой сети, точке входа и операции. Зафиксировать воспроизводимый медленный сценарий либо честно указать, что причина не установлена. Не обещать ускорения только за счёт смены архитектуры.

### Первый замер: Authentik с Mac, 24 ноября 2026, 16:02–16:10 UTC

После жалобы на зависание после ввода кода проверили две части пути по отдельности. В свежем профиле Chrome под управлением Playwright открывали страницу входа без учётных данных. Через Chrome DevTools Protocol фиксировали фактический IP, HTTP-статус и время до заголовков (`Network.responseReceived`, `timing.receiveHeadersEnd`). Для каждого входа запускали отдельный браузер, подменяя только разрешение имени; сертификат проверялся по обычному имени. По одному открытию на вариант, не процентили. Время относится к отдельному запросу, не ко всей загрузке страницы.

| Вариант | Фактический IP | HTML до заголовков | Начальный GET шага входа до заголовков | Результат |
| --- | --- | ---: | ---: | --- |
| Обычный DNS | `109.173.40.247` | 798 мс | 830 мс | Форма видна |
| HOME | `109.173.40.247` | 329 мс | 585 мс | Форма видна |
| Moscow | `91.189.82.238` | 1500 мс | 847 мс | Форма видна |
| NL | не установлен | — | — | Нет HTTP-ответа за 9 с; две отдельные попытки curl ранее не установили TCP за 3 с каждая |

**Независимое серверное наблюдение:** в 16:03–16:06 UTC реплика Authentik на `socrat-1` зарегистрировала GET обработчика входа за 18,2 с, POST за 28,3 с и POST с редиректом `302` за 169,3 с. В том же интервале проверки готовности трёх реплик истекали в ожидании заголовков; после инцидента при опросе готовы были две из трёх. Эти проверки не проходят через публичный DNS. Принадлежность POST конкретному пользователю не установлена. Успешный GET формы **не** воспроизводит отправку кода, а недоступность NL из одной сети не означает глобального отказа.

**Дополнение к диагностике:** вести две задачи независимо. Для NL повторить TCP/TLS с другой внешней сети и сопоставить с наблюдениями на входе. Для Authentik сопоставить по UTC хвост задержек GET/POST на каждой реплике, изменения готовности, ожидание подключений и запросов к БД, давление ресурсов и сеть между узлом и БД. Разовый `kubectl top` после задержки её причину не показывает. При повторении отделить время ответа POST от времени следующей навигации после `302`; использовать только обезличенные времена и статусы, не сохранять тела запросов или коды. Не считать смену IP исправлением Authentik, пока отдельно не проверен полный вход.

### Argo CD: проверять карточку Pod, а не только страницу входа

24 ноября около 16:12 UTC проверили прямую ссылку на Pod приложения `schoolbot`. В чистом Chrome через HOME документ пришёл за 58 мс до заголовков, но браузер перешёл на `/login`: это замер загрузки оболочки, не карточки. В логах сервера Argo за соседнее 20-минутное окно были отдельные вызовы `ManagedResources` за 13,25 с, `ListResourceEvents` за 2,29 с и `GetResource` за 1,27 с. Это длительности обработки RPC, не доказательство принадлежности запросов конкретной вкладке. Долгоживущие `Watch` и `WatchResourceTree` не считать признаком медленной загрузки по времени закрытия потока.

Для воспроизведения открыть прямую ссылку с обычной авторизованной ролью наблюдателя; отдельно измерить время до появления дерева, сведений о Pod, событий и первого полезного ответа потока. Сопоставить времена REST-запросов в DevTools с соответствующими RPC Argo по времени UTC. Если задержка внутри RPC подтверждается, проверить обращения к Kubernetes API и состояние кэша Argo, прежде чем менять публичный маршрут. Ошибку запуска контейнера учитывать отдельно от времени отрисовки карточки.

## 2. Выбрать, кто принимает трафик на публичном IP Москвы

**Ответственные:** владельцы платформы и VPN. Сначала сверить живых владельцев портов TCP **и UDP**, правила NAT, HTTP-редиректы, место завершения TLS, SNI/ALPN, резервные пути и протоколы реально поддерживаемых клиентов. Зафиксировать, кто забирает порт после перезапуска. Свериться с [решением по московскому узлу](../decisions/2026-11-13-keep-moscow-as-a-kubernetes-worker.md) и [исключением Monori](../applications/monori/monori-public-entrances.md). Сохранить обезличенный снимок состояния, метрики и порядок восстановления. Не перезапускать рабочий транзит ради инвентаризации.

Целевой путь: **клиент → публичный IP Москвы → московский ingress → Service → готовый Pod**. Проверить прямой и обратный маршруты до тестовых endpoint на `socrat-5` и домашнем узле, включая NetworkPolicy, межсетевой экран и передачу крупных ответов. Наличие Service или пира WireGuard ещё не доказывает независимость: проверить следующий сетевой узел, туннель, DNS, доступ к Kubernetes API и доступность сертификатов. Отдельно проверить обслуживание уже известных маршрутов и получение новых при отказе зависимости.

**Решение до реализации:** если провайдер может выдать отдельный веб-IP и стоимость согласована, предпочесть этот вариант: действующий VPN-вход не меняется. Если IP должен быть общим, сначала собрать прототип с одним публичным обработчиком, который отправляет веб-имена в локальный ingress и сохраняет текущее поведение VPN. Проверить реальные клиенты, в том числе без SNI, с неизвестным именем и с протоколами, отличными от HTTP, где это применимо. Явно описать порт 80 для HTTP-01 и требования UDP. Не пытаться одновременно занять один адрес и порт двумя процессами и не удалять резервную службу. Если совместимость не доказана — отдельный IP или остановка работ. Результат: схема владения портами и проверенный порядок возврата до переключения трафика.

## 3. Объявлять публичный маршрут один раз

**Ответственный:** владелец платформы. Источником маршрута остаются Ingress, Service и TLS Secret приложения. Нужна единая декларация публичных хостов, пространств имён и исключений по входам. До выбора места сверить уже действующие контракты: не считать `deploy/public-web/services.json` полным списком без проверки. Для каждого контроллера из декларации генерировать либо проверять согласованность наблюдаемых пространств имён, RBAC на чтение и класса Ingress. Только один контроллер обновляет статус Ingress; сертификатами управляет только cert-manager. Проверить видимость временного маршрута HTTP-01 и изоляцию закрытых маршрутов, в том числе при wildcard-правилах. Разрешение читать Secrets всего пространства имён — существенное расширение прав; смешанные публичные и закрытые пространства требуют отдельного ревью.

Разделить реализацию на PR: (а) инвентаризация и тесты рендера без кластера; (б) московский тестовый вход; (в) изменение рабочих входов или DNS. За основу взять [чарт внешнего входа](../../charts/traefik-edge/) и [проверку публичных маршрутов](../../scripts/check-public-ingress.py), но не копировать московскому контроллеру привязку NL к узлу, IP и VPN-маршрутам. Тест должен показать, что объявленный хост появляется на нужных входах, закрытый — не появляется, а отдельные политики VPN, Monori, защищённых консолей и протоколов Argo сохраняются. После приёмки обновить раздел публикации в wiki разработчика.

## 4. Проверить на тестовом хосте и постепенно включить DNS

**Ответственные:** сетевой оператор, а для внешней зоны также владелец домена.

1. Начать с нечувствительного тестового сервиса и свободного адреса или порта, не меняя DNS. Направлять запросы принудительно на каждый вход. Проверить цепочку TLS и SNI, тело ответа, редиректы, HTTP-01, большие ответы, интерфейс Argo и используемые им потоки или gRPC, диапазоны RustFS и отказ без авторизации. Проверить активные VPN-сессии и новые подключения. Убедиться, что исходный IP и доверенные прокси обрабатываются правильно, не расширяя доверие ради теста.
2. Доказать независимость Москвы, исключив переход через NL **только для тестового маршрута**. Сопоставить запрос с наблюдениями на московском ingress и backend. Не отключать NL и не разрывать рабочие туннели. Если заявляется устойчивость к отказу HOME, повторить проверку с endpoint вне HOME и перечислить оставшиеся зависимости от домашних БД и томов. Если безопасный эквивалент такого теста невозможен, независимость считать неподтверждённой и не объявлять её пользователям.
3. До переключения согласовать численный бюджет задержки относительно этапа 1. Не должно быть новых отказов TLS, авторизации и VPN; каждый заявленный вход должен возвращать нужный маршрут и ожидаемые байты. Сравнивать p95 отдельно по проблемным сетям, не скрывая их за общей медианой. Наблюдать тестовый сервис не менее 24 часов.
4. Переключить один согласованный хост, сохранить прежний исправный вход и только затем расширять охват. Для `sch1357.ru` авторитетен REG.RU: согласовать с владельцем запись **хоста**, не передавать управление всей зоной. Оставить schoolbot на проверенном входе до приёмки Москвы. Для собственных зон [авторитетные DNS-серверы](../network/public-entry/public-dns.md) должны отдавать согласованный набор здоровых входов **для каждого имени**, а не адрес ответившего NS. Несколько статических A-записей не задают приоритет. До автоматизации определить кворум проверок, условия снятия и возврата адреса без частых переключений, поведение при отказе всех проверок и TTL. Сохранить исключения отдельных хостов; не менять DNS глобально и не публиковать все имена через wildcard.

## Когда остановиться, как откатить и что согласовать

Остановить внедрение при открытии лишнего маршрута, неверном сертификате, регрессии VPN, повторяющихся тайм-аутах в поддерживаемой сети или неподтверждённом пути до backend. Сначала отозвать тестовую публикацию или новый адрес; пока не истечёт TTL, по возможности безопасно обслуживать закешированные ответы. По согласованному регламенту восстановить прежнего владельца порта и VPN. Откатить только затронутые изменения в GitOps, затем независимо проверить старый веб-вход, DNS и VPN. Не синхронизировать массово приложения Argo и не очищать правила межсетевого экрана. В отчёте зафиксировать замеры до и после, проверенные сценарии отказа и оставшиеся исключения.

**Решения для ревью:** согласовать объём замеров и московский тестовый вход; назначить ответственных за сеть, VPN и DNS. После отчёта о совместимости выбрать отдельный IP или общий обработчик. Окно переключения, пороги приёмки и первый рабочий хост согласовать отдельно. Мерж плана сам по себе не разрешает никаких изменений в продакшене.
