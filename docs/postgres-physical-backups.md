# PostgreSQL physical backups

Both tiers: nightly at 01:30 UTC via a lingering user systemd timer on socrat-0. Owner files: `scripts/postgres/`. A fresh CNPG primary lookup, certificate-verified replication connection, PostgreSQL 18 `pg_basebackup -X stream`, and `pg_verifybackup` precede encryption. `socrat-3:~/backups/pg-platform/<UTC run>/` holds CMS ciphertext and SHA-256 sidecars. Run keys are tier-specific. The receiver checks the digest before atomic non-overwriting publication; SSH sender key is source- and forced-command-restricted. No DB or decryption key is deposited on the receiver. The administrator's separate recipient key is in `~/.config/homelab/pg-platform-dr/recipient.key`. Loss of that key makes the copies unusable; arrange independent secure key escrow. No key material belongs in Git.

Check `systemctl --user list-timers pg-platform-backup.timer` and `journalctl --user -u pg-platform-backup.service` on socrat-0. Expect two success receipts per run. A partial file, free space alert, successful timer invocation alone, or live replica is not a verified restore. Conservative headroom check on receiver; no automatic expiration. Sender and receiver share infrastructure; this does not establish geographically independent DR. Production secrets, application blobs and cluster control plane are not covered.

## Restore drill

First completed pair: `20261121T081807Z`. Both encrypted archives were read back from socrat-3, checked against the recorded digest, decrypted on the administrator host, extracted and independently `pg_verifybackup`-checked. The restored PostgreSQL 18.7 servers were each started and queried in a disposable container with `--network none`, no production mounts, a private Unix socket and fresh recovery-safe config. All seven application DB names were observed. No production restore, client or login was run. Do not unpack into a live PGDATA or reuse the production replication settings.

To repeat: copy the pair of `.cms` and `.cms.sha256` files to a private workspace, verify SHA-256, decrypt with `openssl cms -decrypt -binary -inform DER -inkey <recipient.key> -in <tier.cms>` into the isolated restore environment, extract and verify **before** changing config. Only then remove replica signals, override config for an offline startup, start and query the recovered server. Remove plaintext workspace afterwards. Use an appropriate least-privilege, isolated recovery plan for a real incident.

**Recovery boundary:** this is a full recoverable snapshot per tier and run, not continuous WAL archival, cross-cluster atomicity, or recovery to any chosen timestamp. A failed run extends the potential loss window. Native archive/PITR acceptance requires an independent archive, continuous segment and timeline history across switchovers, and a drill recovering to a named time between two transactions.
