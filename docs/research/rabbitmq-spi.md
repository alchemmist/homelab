# Shared RabbitMQ on Socrat and SPI Triage: research / proposed ADR

2026-11-22. Read-only inventory, not an accepted deployment change. No message payloads, issue bodies, credentials or user IDs were collected. No load, failover or writes in production. Numbers below are observations, not SLOs.

## Why, and where not to use AMQP

Adopt a shared AMQP service if the goal is to isolate producers and consumers, survive consumer downtime and offer that contract to other teams. Do not justify three brokers solely by SPI throughput. An alternative is PostgreSQL with the same durable scheduler plus LISTEN/NOTIFY as a non-durable wake and polling as recovery: fewer failure domains, perfectly viable for SPI alone. Avoid building two competing systems of record. A raw AMQP job queue as a replacement for all SQLite tables is rejected: AMQP acknowledgements cannot atomically commit an incident update, release a budget reservation, change a GitHub issue or recall a Telegram message. RabbitMQ Streams are not necessary for targeted job dispatch; audit/replay should use explicit application records.

## Current production contract

* `automation/spi-triage` and `spi-queue-ui` each 1/1. One worker, Recreate recovery, local RWO source `spi-triage-socrat5`. `Socrat Alerts` and `SPI Incident Triage` are active n8n workflows. `/enqueue-group` atomically admits normalized events; repeat `event_key` increments `deliveries`. `episode` is not a unique job ID.
* `core.py:Store._schedule`, `claim`, `reserve_dispatch`: the highest ready stage wins, then oldest creation/ID. A bounded LLM admission hold can delay new matching. One singleton HTTP wake reservation; ambiguous dispatcher HTTP results wait for claim or retry. `dispatcher.py` posts a wake with an empty body, not a self-contained task. `service.py` exposes claim and match/collect/analyze/publish callbacks. `durable_wait.py` owns execution, stage, deadlines, fences and execution tombstones. A waiting owner releases the HTTP lock, **not** the logical slot. Recovery of an uncheckpointed ambiguous side effect is not blind replay. Do not enable multiworker `recover_on_start` unchanged.
* Critical transactions also cover checkpoints, snapshot replacement limits, independent failure and output budgets, LLM reservations (one active call; rolling count and token limits), cancellation compare-and-set, publication intent, delivery correlations and operator audit. UI list/cancel must work even when RabbitMQ is down. Keep queue history in SQL. S3 evidence is already enabled; object bodies do not belong on AMQP.
* `spi.sqlite` main file: 853,835,776 bytes (~814 MiB), 19 tables. In the observed 24h: 484 new jobs, 530 recorded deliveries for that creation cohort, peak 45 new jobs in a minute. Instantaneous: 5 queued, 1 processing; 2,182 complete, 724 cancelled, 24 dead and 2 dry runs. This is not a long-term distribution. A separate historical SQLite file is not another running queue. Do not copy, publish or delete it in this project.
* Existing tests in `tests/spi_triage/` cover completion ordering, admission, snapshot consistency, durable wait/recovery, duplicate publication and receipts, operator actions and Telegram delivery. Reuse these contracts rather than replacing them with broker-only tests.

## Proposed end state and delivery protocol

* `rabbit-common`, own namespace, initially one tenant vhost `spi-prod`. Separate `spi-test`; separate credentials and permissions per publisher and subscriber, definitions administered by the platform. `pg-common/spi_triage` for authoritative state, unless operations explicitly assigns a critical tier. No dependency on `pg-critical` for RabbitMQ metadata. No changes to other tenants or the n8n execution backend.
* Start with **wake transport**, not four independent stage queues. `n8n → existing SPI HTTP admission → transaction(jobs + outbox)`; outbox relay → topic/direct exchange `spi.events.v1`, routing key `scheduler.wake.v1` → durable quorum `spi.scheduler.v1` → one SPI bridge → current fenced scheduler/n8n workflow. A wake means “inspect due work”, not “run job X immediately”. Preserve current claim ordering and budget across manual, timer and redelivery paths. Time-based retries are SQL `available_at` / owner deadlines plus a timer; the timer emits a wake even if no new arrivals. Do not poll only on inbound alerts.
* Minimal envelope: `schema_version`, `message_id` (outbox PK), type, creation time, opaque correlation ID if needed. No raw alert, token, prompt, output or evidence. Publisher marks sent only after publisher confirm **and** absence of a mandatory unroutable return. Disconnect/negative confirm ⇒ keep outbox row. Retain sent rows for bounded diagnostics, garbage-collect by policy. Remote HTTP producer gets success only after SQL commit; if PG unavailable return retryable failure, not a false acceptance. Broker unavailable but SQL healthy ⇒ intake continues until an explicit outbox size/age limit, then backpressure with an alarm.
* Consumer manual ack after a DB transaction records receipt and a recoverable scheduler wake/reservation, **not** after six-hour workflow completion. On duplicate receipt re-check outstanding wake state; never treat a receipt as proof of external publication. Loss after commit but before ack is benign. A separate reconciler re-drives due SQL work and expired reservations if the bridge dies after ack but before HTTP. A 2xx from n8n is not ownership; fenced claim is. Invalid versions or malformed envelopes go to bounded quarantine; infrastructure failures back off, no immediate nack/requeue spin. For guaranteed broker-side dead-lettering, verify quorum at-least-once dead-letter strategy and compatible overflow config; plain DLX is not by itself a no-loss promise. No automated DLQ replay into production.
* PostgreSQL port: use SQL row locks or transaction-scoped advisory locks for global logical slot / LLM ledger, unique keys for event ID and callbacks, version predicates for stage and cancellation, database time for leases. SKIP LOCKED is useful for outbox publishers, not sufficient to enforce a singleton global budget. Preserve exact IDs, JSON comparison semantics, UTC deadlines, tombstones, and link/upload intent across all 19 tables. No dual execution. No exactly-once claim for externally visible effects.

## Platform footprint and isolation

* No RabbitMQ CRDs or running RabbitMQ pods found on Socrat. Upstream release API at research time: server `v4.4.1`, Cluster Operator `v2.23.3`, Messaging Topology Operator `v1.20.6`. These are **candidate** versions, not a verified compatibility set. Verify supported version pairing, image platforms/digests, Kubernetes compatibility, CRD upgrade procedure, webhook TLS and release notes in a disposable namespace first.
* Cluster Operator for lifecycle; declarative vhosts, exchanges, bindings, policies and users with Topology Operator if compatibility/overhead is acceptable. GitOps ordering: CRDs → operators/webhook readiness → cluster/TLS → tenant topology → client Secrets/NetworkPolicy → application. No public management ingress; AMQPS only, verify server hostname and CA. Restrict 5671 to tenant clients; peer-discovery/distribution ports between brokers only. Metrics scraped privately; vhost limits, connection/channel limits, maximum queue bytes/length, message TTL where loss is explicitly allowed. Enforce an envelope-size cap and use reject-publish rather than silently dropping oldest required work. Brokers still share disk/memory alarms; vhosts are not physical isolation.
* 3 brokers, quorum queue group size 3, hard hostname anti-affinity, PDB `minAvailable: 2`, one-at-a-time upgrades and drain checks. A single-node loss should retain quorum; two unavailable is a real outage. Quorum is not a backup. For SPI, wake queues can be reconstructed from authoritative SQL using a fenced reconciler; future tenants needing irreplaceable messages require their own durability/restore agreement. TLS/Secret rotation and definitions recovery are separate from message replay.
* Placement is a real gate: `local-ssd` currently allows **only socrat-5**; default SC is `nfs-shared`. Do not deploy a 3-node chart with either default. Likely candidates 0/1/5 (CPU/memory requests at inspection roughly 29%/76%, 12%/41%, 55%/50%). These also host all three `pg-critical` members; 0/5 host `pg-common`. Host separation is not disk isolation. Verify actual spare disks, latency, endurance, fsync p95/p99 and network RTT per pair, especially under PG checkpoint/backup load. Prefer three explicit node-local dedicated PVs, WFFC and Retain. Do not reuse a PG data volume or label an HDD as SSD. If insufficient, provision capacity or defer HA rather than collocate replicas on one disk. Size queue/PVs from measured peak, outage backlog and catch-up rate, not from the 814 MiB SQLite file.

## Experiments, acceptance and rollback

1. Establish a 7-day baseline: unique arrivals, bursts, stage latency and backlog age; time to claim excluding intentional wait; ambiguous external actions; SQLite/WAL growth; node I/O and PG commit latency. Inventory current n8n ingress authentication, timeout/HTTP retry handling and existing operational SLOs. Agree RPO/RTO and outage envelope before choosing disk limits.
2. Disposable RabbitMQ + synthetic producer/consumer: verify TLS, ACL denial across vhosts, routed confirms, duplicate handling, disk/memory alarms, leader restart, minority partition, two-node loss and recovery. Run no production publishers, jobs, credentials, alerts or mutations. Exercise independent client reconnect and endpoint discovery. Test losing a local-PV node, not just deleting a pod.
3. Port SPI SQL state separately; isolated trusted copy if needed, normalized row-by-row reconciliation across every table, audit budgets and ownership independently. Workload with fake GitHub/Telegram/model/evidence and no routes/credentials to real services. Competing claims, duplicate group, stale callbacks, cancel-vs-publish race, paid-call timeout, pause/restart through Wait, Kafka-style offset assumptions explicitly absent. Preserve external-effect ambiguity for manual review. Compare deterministic next-claim traces and terminal outcomes, not just counts.
4. Enable transactional outbox in shadow mode: isolated vhost and sink that can **never** wake n8n. Compare admission commits against distinct confirmed wake IDs and overdue runnable jobs. Inject confirm loss, mandatory return, consumer death before/after commit/ack, broker outage with continued intake, expired lease and outbox replay. Prove zero lost admitted jobs, zero duplicate paid calls/publications in simulated faults, bounded backlog catch-up, one logical owner. Set alerts on oldest unseen outbox record, oldest due unowned job, blocked publishers, redelivery, quorum state, DLQ, disk alarms, PG contention and n8n orphan waits.
5. Promote one dispatcher generation at a time. For final SQLite→PG copy, pause/buffer ingress with an explicitly tested upstream retry contract; finish or safely fence in-flight n8n owners, preserve tombstones, stop every SQLite writer, cold import, verify receipts. Do not acknowledge intake into a stopped writer. Prefer a separate window for switching HTTP-wake to AMQP-wake. Fallback after PG writes is to the old **dispatcher** operating against the same PG state, not to old SQLite. Stop shadow/publisher consumers and fence obsolete generation before resuming. Verify public status and actual authorized paths without triggering a real incident as a test.

## Decision

Proceed with a disposable broker/transport PoC and capacity measurement, not a production install. Keep n8n and the one-owner execution contract in v1. Only consider replacing n8n stage orchestration or adding tenant #2 after the first design has demonstrated operational value. First deliverables: measured node/PV candidates, compatibility table, failure-test report and a go/no-go decision.
