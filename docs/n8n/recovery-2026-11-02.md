# n8n recovery, 2026-11-02

## Incident

After the Fleet → Argo CD transition, n8n was using a PVC created at
2026-11-01T22:33:11Z instead of its original volume. It had no configured owner,
workflows or credentials. The old directory was not present. Exact destructive
operation has not been established; timing alone is not proof of which command
removed it. Do not create a replacement owner as an incident workaround.

The transition also omitted the n8n private-gateway vhost and removed the native
public TLS ingress. The Authentik gateway now owns an independent TLS certificate.
The repaired WG vhost forwards to Traefik HTTPS, preserving Authentik UI and native
machine endpoint policies rather than bypassing authentication.

## Recovery performed

Read-only raw scanning of the socrat-1 ext4 partition located surviving SQLite
rollback-journal pages. A plain contiguous carve was not a valid database.
Recovered complete SQLite records, including overflow chains where available,
were used to reconstruct application state in a schema-compatible database.
This is forensic reconstruction, NOT an intact original database-file recovery.
No new owner account or replacement password was created.

Recovered:

- original owner ID, password hash and account settings;
- four encrypted credential records; successful decryption with the retained
  n8n encryption key, including Google OAuth token data;
- original public API and MCP key records;
- Calendar and Blog Updates workflows with original IDs, node definitions and
  available static state; original personal-project identity and ownership;
- required workflow-version records and validated foreign-key relationships.

Limits: execution history and every historical workflow version were not fully
recovered. Recovered records came from different surviving journal snapshots;
this is not a transactionally exact point-in-time copy. Latest recoverable Google
credential was dated 2026-11-01 22:30:18.702. Calendar definition recovered from
2026-10-30 13:53:45.706; Blog Updates from 2026-10-31 19:21:08.075.

## Installation and verification

Paused n8n auto-sync during replacement, stopped the only application writer,
installed verified SQLite on the mounted PVC, and preserved the previous empty
SQLite files separately. Returned Argo auto-sync and node scheduling to their
previous state. Activated both workflows through the recovered original API key.

Checks:

- SQLite integrity_check: ok; foreign_key_check: zero violations;
- original API key lists both workflows;
- n8n settings report showSetupOnFirstLoad=false;
- repeated Calendar scheduled executions succeed using recovered Google OAuth;
- Blog Updates retains its four English nodes and production writes remain off;
- original password hash is retained; human browser login is not asserted tested.

A registered duplicate GitHub webhook for the exact same URL was removed after
reactivation. Never delete unrelated repository hooks during recovery.

## Backups and prevention

Verified reconstructed database and original encryption Secret are saved privately
off-node under the operator's recovery directory, outside git. Raw pages, SQL
records, tokens, password hashes and database files must NEVER be committed.
The initial full-device capture failed due to a streaming timeout and is only a
partial artifact, not a valid disk backup. Do not treat it as complete.

PV reclaim policy was set to Retain. The PVC template now has Helm keep and Argo
Prune=false,Delete=false annotations. These reduce accidental lifecycle deletion;
they are not backups and do not protect against arbitrary manual host deletion.
Before a future release-manager migration, take and verify an off-node consistent
SQLite backup plus its encryption key, preserve the existing PVC/PV identity and
check account/workflow/credential counts after cutover, not just /healthz.
Recurring verified off-node backups still need a dedicated implementation.
